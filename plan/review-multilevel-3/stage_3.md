## 3.1 Д7 — прогоны рампы идут из ядра, а не строятся вторым обходом

**Проблема.** `src/client/parts/rampRuns.js` — независимая реализация
`MapLevels::build_runs` (E `map.rs`) на другом языке. Её собственный
комментарий (строки 8-13) требует «кроме ширины прогона эти два
представления разъезжаться не должны ни в чём», но ничто этого не
проверяет. Расхождение даёт горку, которую видно и нельзя проехать (или
наоборот) — тихий отказ.

**Решение (принято).** Отдать прогоны из ядра. Оно их уже строит, и
клиентская реплика их уже получает: `ClientMapConfig::take_levels`
(`core/src/client/mod.rs:105-113`) → `MapLevels::runs()`. Порядок вызовов
на клиенте это позволяет: движок зовёт `clientCore.set_map(...)`
(`packages/engine/src/client/main.js:580`) ДО `createMap(...)`
(`main.js:693`), то есть на момент конструирования парта карта в ядре уже
загружена.

1. **ABI.** В `core/src/lib.rs`, рядом с `map_dynamics_to_world`
   (`lib.rs:117`), добавить запрос:

```rust
/// Прогоны рамп текущей карты для РЕНДЕРА клина: тот же
/// `MapLevels::runs`, по которому физика ставит стражей. Второй обход
/// грида на JS расходился бы с ядром молча — горка, которую видно и
/// нельзя проехать.
/// Формат: JSON-массив
/// `{ axis, sign, from, to, min, max, crossMin, crossMax, block }`,
/// координаты — МИРОВЫЕ (уже масштабированные), как в `RampRun`.
/// Пустой массив — карты нет или она одноуровневая.
pub fn ramp_runs(&self) -> String
```

   Источник — `MapLevels` предиктора (`Predictor::levels()`,
   `core/src/client/predictor.rs:367`). Если у карты нет уровней, вернуть
   `"[]"`.

2. **Сервис.** В `src/client/index.js`:
   - `serviceNames: ['levelView', 'mapDynamics', 'rampRuns']`;
   - в `hooks.services(core)` добавить

```js
// прогоны рамп из ядра: клин рампы рисуется по ТОЙ ЖЕ геометрии, по
// которой физика ставит стражей прогона. Второй обход грида на JS
// расходился бы с ядром молча
rampRuns: {
  // прогоны текущей карты; [] — карты нет или она одноуровневая
  forLevel(level) {
    return JSON.parse(core.ramp_runs()).filter(run =>
      Math.min(run.from, run.to) === level || Math.max(run.from, run.to) === level,
    );
  },
},
```

   Точный предикат фильтра выбрать по тому, какой слой рисует клин: сейчас
   его строит слой, в чьих тайлах лежит рампа, то есть уровень `from`
   (`packages/engine/src/client/main.js:667` фильтрует `ramps` по
   `ramp.from === level`). Значит фильтр — `run.from === level`.

3. **Конфиг.** В `src/config/client.js`, `componentDependencies`, добавить

```js
// прогоны рамп из ядра: по ним слой строит клин горки (см. решение 2
// плана review-multilevel-3)
rampRuns: ['Map'],
```

   Контрактный чекер (правило C4) сверяет `componentDependencies` со
   `serviceNames` — оба списка обязаны знать имя.

4. **Парт.** `src/client/parts/Map.js:315-317`:

```js
const runs = this._ramps.length ? buildRampRuns(this._map, this._ramps) : [];
```

   заменяется на чтение сервиса и перевод мировых координат в клетки
   (у парта `this._step` — НЕмасштабированный шаг, `this._baseScaleX/Y` —
   масштаб карты; в ядре `tile_size == step * scale`):

```js
// прогоны приходят из ядра в МИРОВЫХ единицах, а грид слоя не
// масштабирован: перевод один и тот же, что у `_hasLayerTileAt`
const toCell = (world, scale) => Math.round(world / scale / this._step);
```

   `col0 = toCell(run.min, this._baseScaleX)` и так далее по оси прогона;
   поперёк — из `crossMin`/`crossMax`.

5. **`rampRuns.js`.** Обход грида (`buildRampRuns`, строки 30-116) и таблица
   `DIRS` удаляются целиком. Остаётся `mergeLanes` — визуальная склейка
   полос, которая теперь группирует по `run.block` (полосы одной горки
   несут один номер, E `map.rs:730-734`), а не по строковому ключу
   `axis|sign|rise|along`. Файл переименовывается в
   `src/client/parts/rampLanes.js` либо оставляет имя с новой докстрокой —
   выбрать и записать сюда.

6. **Тесты.** `tests/client/parts/rampRuns.test.js` переписывается: на вход
   идут прогоны в формате ядра, проверяется склейка полос по `block` и
   перевод в клетки. Тесты обхода грида удаляются вместе с обходом.
   `tests/config/client.test.js` — проверить, что `rampRuns` объявлен и в
   `serviceNames`, и в `componentDependencies`.

**Побочный выигрыш:** Д12 (см. 3.3) исчезает по построению — клетки
раздаёт ядро.

## 3.2 Д6 — нисходящая рампа не рисуется (тихий отказ)

**Проблема.** `src/client/parts/rampRuns.js:67-71`:

```js
const rise = (Number(ramp.to) || 0) - (Number(ramp.from) || 0);

if (rise <= 0) {
  continue;
}
```

Движок нисходящую рампу поддерживает явно: `low = ramp.from.min(ramp.to)`,
`high = max` (E `map.rs:304-305`), `rise = (to - from).abs()`
(E `map.rs:1174`), а валидатор запрещает только `from == to`
(E `map.rs:259-261`). Карта с `{ from: 1, to: 0 }` получает полноценную
физику горки — прогон, уклон, стражей — и НИ ОДНОГО пикселя картинки: ни
клина, ни юбки.

**Решение.** После 3.1 знак берётся из данных ядра, но высоты в
`Map.js` по-прежнему считаются от `this._level`:

- `Map.js:391` — `const kBase = this._level * shear;`
- `Map.js:412` — `const k = (this._level + run.rise * progress) * shear;`
- `Map.js:488` — `k: (this._level + run.rise) * shear,`

Для нисходящей рампы `this._level` — это ВЕРХНИЙ уровень прогона
(рендер-слой выбирается по `ramp.from`, `main.js:667`), и подъём идёт от
него ВНИЗ. Заменить базу на нижний уровень прогона:

```js
// базовая плоскость прогона — его НИЖНИЙ уровень: у нисходящей рампы
// (`from > to`) тайл лежит в гриде верхнего, и клин растёт от нижнего
// вверх, а не от слоя вниз
const low = Math.min(run.from, run.to);
const rise = Math.abs(run.to - run.from);
const kBase = low * shear;
const k = (low + rise * progress) * shear;
```

`progress` по-прежнему берётся из `run.sign` (`Map.js:411`) — знак задаёт,
с какого конца прямоугольника подъём, и для нисходящей рампы он уже
правильный, потому что приходит из ядра.

**Тесты** (`tests/client/parts/Map.test.js`): карта с
`ramps: [{ tile: N, dir: 'east', from: 1, to: 0 }]` — клин строится,
высота вершин меняется от `0` до `1 * shear`, юбка стоит на `kBase = 0`.

## 3.3 Д12 — прогон занимает клетки, отданные другой рампе

**Проблема.** `rampRuns.js:43-58`: если свободна была хотя бы ОДНА клетка
прямоугольника, прогон пушится во всю ширину, включая клетки, уже отданные
другой рампе. Сейчас недостижимо — движок запрещает пересечение рамп
(фикстура `packages/engine/contract/fixtures/layered/bad-ramps-overlap.json`),
— но зависимость нигде не записана.

**Решение.** После 3.1 функция `push` удаляется вместе с обходом, и дефект
исчезает. Если по какой-то причине 3.1 не сделан — усечь прогон по
фактически занятым клеткам и сослаться в комментарии на фикстуру движка.
В этом случае пункт помечается «оставлен, причина: …».

## 3.4 Д16 — парт получает `levelHeight` и не использует его

**Проблема.** Движок кладёт в данные статического слоя
`levelHeight` (`packages/engine/src/client/main.js:646, 663`) с
комментарием «партам нужен для параллакса слоёв и экструзии объёмов», но
`src/client/parts/Map.js` его нигде не читает: высота в рендере мерится
УРОВНЯМИ и умножается на `parallax.shear` (`src/config/render.js`).
То есть карта с нестандартным `levelHeight` меняет физику подъёма, но не
меняет картинку — клин будет той же крутизны, что у карты с высотой по
умолчанию.

**Решение — принять и записать одно из двух:**

- **(а) Считать это верным** и убрать вводящий в заблуждение комментарий в
  движке (`main.js:645-646`), а в `docs/en|ru/configuration.md` записать
  прямо: `levelHeight` — величина ФИЗИКИ, вертикальный масштаб рендера
  задаёт `parallax.shear` и он намеренно не зависит от карты, иначе слои
  разных карт разъезжались бы по виду.
- **(б) Связать их**: `shear` умножается на `levelHeight / tileSize`, тогда
  крутая карта и выглядит круче. Дороже: меняет вид ВСЕХ существующих карт
  и требует пересъёмки приёмки этапа 6.

Рекомендация — **(а)**: `shear` подбирался на глаз под читаемость, а не
под геометрию. Решение записать в этот пункт с обоснованием.
