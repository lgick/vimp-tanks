# Этап 7. Ночь и освещение ✅ выполнен

> **Согласованные отступления от плана (решения пользователя при выполнении):**
> 1. Вместо `RenderTexture` + `renderer.render` карта освещённости уровня — контейнер-оверлей на сцене с проходным
>    фильтром (`resolution = lighting.resolution`, `blendMode = 'multiply'`). Причина: `onRender` вызывается внутри
>    кадра после `renderStart`, вложенный рендер в RT сбросил бы стек целей PixiJS. Раскладка источников — раз на
>    трансформ сцены в тике; RT не пересоздаются (текстуры фильтра пуловые).
> 2. В API сервиса добавлен геттер `lighting.texture(name)`: `Tank` берёт текстуру `head` для бликов фар, сервис
>    подменяет её у бликов при повторной `registerTextures`.

**Репозиторий:** `vimp-tanks`. **Зависит от:** этапа 1 (поле `game` доходит до частей).
**Перед началом:** `plan/night-city/README.md` → «Общий контекст»; `docs/en/architecture.md` → «Draw order across levels (2.5D)»
целиком; скилл `pixijs-blend-modes` и `pixijs-performance` (PixiJS v8).

## Цель

На картах с `game.lighting.night: true`:
- сцена погружена в полумрак, но враги различимы (только атмосфера);
- фонари дают тёплые пятна на своём уровне;
- у каждого живого танка два конуса фар по курсу корпуса;
- неон и головы фонарей светятся поверх темноты;
- вспышки взрывов и выстрелов кратко подсвечивают окрестность.

Свет уровня 0 не освещает мост уровня 1, а мост не затемняется дважды. Радар не меняется.
`render.js → lighting.enabled = false` полностью отключает систему.

## 7.1 Техника (обязательная для реализации)

Для каждого уровня `L`, присутствующего на карте, — своя **карта освещённости** (`RenderTexture` размером с вьюпорт ×
`lighting.resolution`) и **спрайт-оверлей** на сцене:

1. Оверлей уровня `L` — ребёнок сцены, `zIndex = levelZ(LIGHT_OVERLAY_BASE_Z = 40, L)`, `blendMode = 'multiply'`.
   Каждый кадр он растягивается на экран контр-трансформом сцены: `position = −stage.position / stage.scale`,
   `scale = 1 / stage.scale` (с учётом разрешения RT).
   База 40 выше всех динамических частей своего уровня (`Tank` 3, дым 4, окклюдер объёмов 5) и ниже шага 100.
   Слои карты с базой `≥ 40` запрещаются проверкой в тестах для ночных карт.
2. Содержимое карты освещённости уровня `L` (рендер в RT, один раз на новый трансформ сцены — по ключу кэша камеры
   `levelView.camera()`):
   - **`L = 0`**: очистка цветом `ambient`; источники уровня 0 — аддитивно.
   - **`L ≥ 1`**: очистка **белым** (multiply на белый не меняет картинку); затем **маска этажа** — `Graphics`
     с прямоугольниками клеток `floor` уровня `L` (перила уже входят в `floor`), залитыми `ambient`, в проекции уровня (`offsetPoint`,
     `k = L · parallax.shear`); затем источники уровня `L` — аддитивно. Вне этажа RT остаётся белой (выше 1 значения
     обрезаются), поэтому уровень 0 не затемняется второй раз.
   - Координаты мир → экран: `offsetPoint(x, y, camera, k)`, затем трансформ сцены (как в `holeOverlay.js` ≈54–64).
3. **Прозрачность над игроком**: оверлей уровня выше игрока получает ту же дыру, что и плита
   (`holeOverlay.apply` с тем же конфигом; в режиме `'layer'` — `alpha` слоя). Иначе в дыре останется тёмное пятно.
4. **Эмиссивный слой** уровня `L`: контейнер на сцене с `zIndex = levelZ(EMISSIVE_BASE_Z = 45, L)` и аддитивными спрайтами
   (головы фонарей, блики фар, неон этапа 8). Прозрачность — через `levelView.alphaFor`.
5. Производительность:
   - RT на `lighting.resolution` (по умолчанию `0.5`);
   - отсечение источников по экранному прямоугольнику;
   - лимит `lighting.maxLights`;
   - все источники используют 2 запечённые текстуры, поэтому батчатся;
   - оверлей уровня `0` создаётся **всегда** на ночной карте (полумрак нужен всей земле); оверлеи уровней `L ≥ 1` —
     только если у уровня есть этаж (непустая маска `setLevelMask`).
   RT пересоздаются при изменении размера экрана.

## 7.2 Конфигурация

1. `src/config/render.js`:
   ```js
   export const lighting = {
     enabled: true,
     resolution: 0.5,
     maxLights: 96,
     headlights: { length: 90, spread: 0.55, intensity: 0.9, color: 0xfff1c4, offset: 0.5, glareSize: 6 },
     tankGlow:   { radius: 26, intensity: 0.35, color: 0xbfd0ff },   // слабый свет под каждым танком — видимость врагов
     flash:      { explosion: { radius: 140, intensity: 1.0, duration: 260, color: 0xffb060 },
                   shot:      { radius: 40,  intensity: 0.6, duration: 70,  color: 0xfff0a0 } },
   };
   ```
   Экспортировать и из `src/config/client.js` (как остальные блоки render.js, ≈221–226).
2. Поле карты:
   ```js
   game: { lighting: {
     night: true,
     ambient: 0x3a4260,                  // цвет полумрака (яркость ≈ 0.35–0.45, враги различимы)
     lamps: [ { cell: [12, 30], level: 0, radius: 110, color: 0xffc070, intensity: 0.9, head: true, flicker: 0 } ],
   } }
   ```
   Позиция — клетка сетки `[col, row]` (центр клетки; не масштабируется движком). В данных статической части `step`
   **не масштабирован**, масштаб лежит отдельно в `data.scale` (`vimp/packages/engine/src/client/main.js` ≈651–676,
   `MapLayer.js` ≈50 через `baseScale(data.scale)`). Мировая позиция — `x = (col + 0.5) · step · scale`;
   точную формулу мировой клетки взять из `tileGrid.js` (`cellOfPoint`), не выводить заново.
   `flicker` — `0..1`, сила мерцания.

## 7.3 Бейкеры

- `lightRadialTexture` — радиальный градиент от белого к прозрачному (плавный спад, без жёсткого края).
- `headlightConeTexture` — клин с мягкими краями и спадом по длине; вершина в точке (0, 0.5).
- `lampHeadTexture` — маленький яркий диск с ореолом (эмиссив).
Регистрация в `bakers/index.js` и `bakedAssets` (компонент — `Tank` для конуса, `Map` для остальных; сервис получает
текстуры через части, которые их регистрируют). Ни одна часть не владеет всеми тремя, поэтому регистрация
**частичная**: `Map` передаёт `{ radial, head }`, `Tank` — `{ cone }`, сервис сливает переданные ключи.
Зависимости от наличия текстур:
- фонари (источники и головы) создаются, когда есть и ключ карты, и `radial`/`head` — в каком бы порядке ни пришли
  `acquireMap` и `registerTextures`;
- `addLight({ kind: 'cone' })` без `cone` и `flash` без `radial` — no-op без ошибки (вспышка от `ExplosionEffect`
  зависит от `radial`, который регистрирует `Map`);
- `registerTextures` всегда **перезаписывает** переданные ключи; `clear()` текстуры не трогает (7.4, «Два вида
  состояния»). После перепечки при потере контекста пересозданные части передают свежие текстуры, и мёртвые
  заменяются сами.

## 7.4 Сервис `lighting` (`src/client/lighting/`)

Файлы: `createLighting.js` (фабрика сервиса), `LevelLightMap.js` (RT + оверлей + маска уровня), `lightMath.js`
(чистые функции: проекция, отсечение, мерцание — тестируемые), `index.js`.

API (возвращается из `hooks.services(core)`; `'lighting'` добавить в `serviceNames` и `componentDependencies` для
`Map`, `Tank`, `ExplosionEffect`, `ShotEffect`):

```js
lighting.enabled                                   // false → все методы no-op
lighting.attachStage(stage, renderer)              // идемпотентно, как levelView.attachStage
lighting.acquireMap(mapKey, lightingCfg, step, scale) // каждая статическая часть; первый вызов НОВОГО ключа инициализирует (или переключает), остальные +1 к счётчику ключа
lighting.releaseMap(mapKey, owner)                  // из destroy() части; снимает маску owner; счётчик ключа на нуле → clear() только если ключ текущий
lighting.setLevelMask(level, cells, owner)         // клетки этажа уровня ≥1; вклад принадлежит части owner, маска уровня — объединение вкладов
lighting.registerTextures({ radial?, cone?, head? }) // частичная: сливается с уже переданными (7.3)
const h = lighting.addLight({ level, x, y, z, kind: 'radial'|'cone', radius, rotation, color, intensity })
lighting.updateLight(h, patch); lighting.removeLight(h)
lighting.flash({ level, x, y, z, radius, intensity, duration, color })
lighting.addEmissive(sprite, level) -> boolean     // false — эмиссивного слоя нет, спрайт остаётся у вызывающего
lighting.removeEmissive(sprite)
lighting.isNight()                                 // enabled && night у текущей карты
lighting.render()                                  // вызывается частями из onRender; реальная работа — раз на трансформ сцены
lighting.clear()                                   // внутренний: из releaseMap, когда обнулился счётчик ТЕКУЩЕГО ключа; освобождает ТОЛЬКО состояние карты (сначала со сцены, потом destroy)
```

`night: false` или отсутствие `game.lighting` → оверлеи не создаются, источники игнорируются.

**Два вида состояния.** Движок применяет карту так: сначала `removeMap(currentMapSetId)`, потом
`createMap(setId, staticData)` (`vimp/packages/engine/src/client/main.js` ≈697–698). Старые части карты уничтожаются
**до** создания новых, поэтому счётчик текущего ключа падает до нуля и `clear()` срабатывает при **каждом**
применении карты. Танки и эффекты — не части карты (`removeMap` удаляет только `gameSets[setId]`) и переживают его.
Поэтому состояние сервиса разделено:
- **состояние карты** — RT, оверлеи, фонари (источники и головы), вклады масок по уровням. Живёт по ключу
  (маски — по владельцам), `clear()` освобождает только его;
- **состояние сессии** — зарегистрированные текстуры, источники от `addLight`, записи эмиссива `(sprite, level)`.
  `clear()` его не трогает. Источники и эмиссив снимает их владелец в своём `destroy()`. Эмиссивные контейнеры
  уровней — отображение списка записей: `clear()` снимает контейнеры со сцены, но записи сохраняет, а `acquireMap`
  новой ночной карты пересобирает контейнеры и возвращает в них спрайты. Пока ночной карты нет, `addEmissive`
  по-прежнему возвращает `false` для новых вызовов, а уже принятые спрайты не рисуются (их контейнеров нет на сцене).

**Эмиссив без освещения.** При `enabled: false` или `night: false` `addEmissive` возвращает `false` и спрайт не
забирает. Вызывающая часть обязана тогда оставить спрайт у себя (головы фонарей — в контейнере сервиса не
создаются вовсе; неон этапа 8 — в контейнере `animated` своего слоя; блики фар — не создаются). Иначе на ночной
карте с `lighting.enabled = false` пропали бы вывески, хотя 9.7 проверяет именно этот режим.

**Потеря WebGL-контекста.** Движок (`vimp/packages/engine/src/client/main.js`, `handleContextRestored` ≈1335) после
восстановления уничтожает все сущности (`CTRL[p].remove()`), заново запекает `bakedAssets` и пересобирает карту.
Сервис же **не часть** — он переживает восстановление и держит мёртвые `RenderTexture` и оверлеи. Поэтому:
- `lighting.clear()` полностью сбрасывает **состояние карты**: снимает оверлеи и эмиссивные контейнеры со сцены,
  освобождает RT и фонари, **забывает `mapKey`**. Без этого повторный `acquireMap` с тем же ключом не
  переинициализирует сервис, и ночь не вернётся;
- `clear()` вызывается сам, когда падает до нуля счётчик **текущего** ключа. Движок при восстановлении
  уничтожает все части (и танки, и эффекты), счётчик обнуляется, а новые части заново делают `acquireMap`
  и создают новые RT;
- состояние сессии при потере контекста очищается без участия `clear()`: все владельцы источников и эмиссива
  уничтожены и сняли своё в `destroy()`, а текстуры перезаписываются свежими при `registerTextures` пересозданных частей;
- тест: `acquireMap ×3 → releaseMap ×3 → acquireMap(тот же ключ)` создаёт новые RT и оверлеи; смена карты в
  реальном порядке движка (все старые части уничтожены, затем созданы новые) освобождает старые RT, новые не страдают.
- `mapKey` собирается **только из данных, которые есть у каждой статической части**: размеры сетки `data.map`
  (у всех уровней одинаковы — `validate_levels` отклоняет несовпадение) + хэш `JSON.stringify(data.game?.lighting)`
  (FNV-1a, `lightMath.js`). `setId` и числа уровней в данных части нет: движок передаёт статической части
  `{type, spriteSheet, map, step, layer, tiles, level, solid, floor, volume, levelHeight, ramps, physicsStatic, scale}`
  плюс `game` с этапа 0 (`main.js` ≈651–676) — ключ на них опираться не может. Функция ключа одна
  (`lightMath.mapKeyOf(data)`), её вызывают все части.
- **Маски принадлежат частям, а не ключу.** Две разные карты с одинаковыми размерами и освещением дают один ключ,
  и это безопасно: фонари у них по определению те же, а маски этажей не зависят от ключа. Каждая часть уровня `L ≥ 1`
  вносит свой вклад `setLevelMask(L, cells, owner)` и снимает его в `releaseMap(mapKey, owner)`; маска уровня — объединение
  текущих вкладов, пересчитывается при изменении. При смене карты старые части снимают свои вклады до того, как
  новые вносят свои, так что маска чужих клеток не содержит. Оверлей уровня `L ≥ 1` исчезает, когда вкладов уровня
  не осталось.
- **Переключение ключа.** Сейчас движок уничтожает старые части раньше создания новых, и штатная смена карты идёт
  через `clear()` → `acquireMap` нового ключа. Переключение при ненулевом счётчике — защита от обратного порядка
  (например, если движок его поменяет): если при `acquireMap` ключ отличается от текущего, а счётчик ещё не ноль,
  сервис освобождает RT, оверлеи и фонари старого ключа и создаёт их для нового (вклады масок остаются у своих
  частей). `releaseMap` со старым ключом только уменьшает счётчик старого ключа (счётчики ведутся по ключам); когда
  он падает до нуля, запись о ключе удаляется, а `clear()` **не** вызывается — иначе он стёр бы уже переключённую
  новую карту.
  Тесты — в **реальном** порядке движка (все старые части уничтожены, затем созданы новые):
  - две карты одного размера с разными `lamps` — видны фонари новой карты, оверлеи на месте;
  - две карты одного размера с одинаковым `game.lighting`, но разными этажами — ключ общий, маска уровня содержит
    только клетки новой карты;
  - **танк жив при смене карты** (ночь → ночь): после `acquireMap` новой карты его конусы светят и блик виден без
    повторных `registerTextures`/`addLight`/`addEmissive`; ночь → день → ночь — блик скрыт на дневной карте и
    возвращается на ночной;
  - отдельный тест обратного порядка (новые части раньше старых) — для ветки переключения.
- Повторная загрузка той же карты в новом раунде даёт тот же ключ: фонари не пересоздаются — так и нужно.

## 7.5 Подключение частей

1. `src/client/parts/map/MapLayer.js`:
   - каждая статическая часть вызывает `lighting.acquireMap(...)` (часть не знает, какие ещё слои есть на карте,
     поэтому «первой части» не бывает — только счётчик);
   - фонари (источники и эмиссивные головы) создаёт **сам сервис** при первом `acquireMap` **нового ключа** из
     `lightingCfg.lamps`, а снимает в двух случаях: в `clear()` и при переключении на другой ключ (7.4). Части фонари не создают: ни одна часть не знает, какие ещё слои есть на карте, и не может
     решить, что владелец — именно она;
   - ключ — `lightMath.mapKeyOf(data)` (7.4), у всех частей одной карты он одинаков;
   - **`acquireMap` и `setLevelMask` вызываются синхронно в конструкторе**, до `_build` и любых `await`. Сборка слоя
     асинхронная (`MapLayer.js` ≈116, `async _build` с `await buildLayerAssets(...)`). Если освещение подключить после
     `await`, сервис станет «ночным» с задержкой. `Tank`, созданный первым кадром, получит `addEmissive → false`
     и останется без бликов до пересоздания (7.5.2), а `NeonSign` навсегда уйдёт в контейнер `animated` (8.4.2).
     Нужные данные (`data.map`, `data.floor`, `data.game`) есть уже в конструкторе. Вывески и декали этапа 8 строятся
     после, в `_build`;
   - часть уровня `L ≥ 1` передаёт свой вклад в маску этажа `setLevelMask(L, cells, this)` (клетки, чей тайл в `data.floor`;
     `walls` — подмножество `floor`, отдельно не нужны). Вклады нескольких слоёв уровня объединяются;
   - в `destroy()` часть вызывает `lighting.releaseMap(mapKey, this)` — это снимает и её вклад в маску. Своих источников у `MapLayer` нет (фонари принадлежат
     сервису); источники неона этапа 8 снимает сама `NeonSign` в своём `destroy()`.
2. `src/client/parts/Tank.js`:
   - живой танк держит 2 конуса и 1 `tankGlow`; позиция — передняя кромка корпуса со смещением `±offset` по ширине;
   - `rotation` = угол корпуса; `level = renderLevel(level, z)`; `z` — для проекции;
   - блики фар — эмиссивные спрайты, отданные в `lighting.addEmissive(sprite, level)`: они живут в эмиссивном
     контейнере сервиса, **не** соседями на сцене. Если `addEmissive` вернул `false` (ночи нет), блики не создаются. При смене отрисовочного уровня танк делает
     `removeEmissive` и `addEmissive` с новым уровнем;
   - обломок (`condition 0`) — фары выключены; `destroy()` снимает всё;
   - смена карты от танка ничего не требует: источники, блики и текстура `cone` — состояние сессии (7.4) и
     переживают `clear()`. Танк не пере-регистрирует их в ответ на смену карты.
3. `ExplosionEffectController` / `ShotEffectController`: `lighting.flash(...)` на уровне эффекта.

## Критерии готовности

Проверки из README зелёные. В `npm run dev` на фикстурной ночной карте:
- под мостом свет фар не выходит на плиту моста;
- на мосту плита освещается фарами только своего уровня;
- дыра над игроком без тёмного пятна;
- FPS на слабом профиле (DevTools CPU throttling 4×) не хуже, чем без освещения, более чем на 15 %.
