## Общая оценка

Архитектура выбрана верно и последовательно проведена через оба репозитория:

* **Единый источник правил.** `core/src/level.rs` (танки) и
  `vimp_engine_core::map::MapLevels` (движок) — единственные места, где живут
  правила уровней; хост и клиентская реплика зовут одни и те же функции.
  `ClientMapConfig::take_levels` отдаёт **одну** `Rc<MapLevels>` и предиктору
  движения, и предиктору выстрела — повторить это разбором JSON дважды было бы
  классическим источником тихого рассинхрона, и этого не сделано.
* **Аддитивность формата.** Карта без `levels`/`ramps` идёт прежним путём
  бит-в-бит: отдельная ветка нав-графа в `game.rs::load_map`, отсутствие
  фильтра групп в `process_hitscan`/`avoid_obstacles`, `ground_only()` в
  `ray_segments`. Формат кадра не менялся (`PLAYER_STATE_LEN = 8`),
  `ENGINE_API_VERSION` не бумпался, ABI расширен append-only.
* **Комментарии объясняют «почему», а не «что»** — редкость; отклонения от
  плана записаны в `plan/done/multilevel-maps/stage_*.md` вместе с причиной.
* **Попутно починен реальный баг**: `players_json` терял `angvel`, из-за чего
  `FIRST_SHOT_DATA` и бинарный кадр имели разную ширину строки `m1`.

Ниже — то, что ревью нашло. Порядок этапов — по стоимости простоя: сначала
то, что не даёт собрать репозиторий, затем мёртвые фичи, затем правила игры,
затем качество.

## Этап 2. Две мёртвые фичи рендера (see-through моста) ✅ выполнен

Ключевая фича этапа 6 — полупрозрачная плита над локальным игроком — не
работает **по двум независимым причинам**. Обе тихие.

### 2.1 `Map.onRender` никогда не вызывается PixiJS ✅ выполнен

**Проблема.** `src/client/parts/Map.js:202` объявляет `onRender()` как метод
класса. В PixiJS v8 `onRender` — это **аксессор**, подмешанный в
`Container.prototype` (`node_modules/pixi.js/lib/scene/container/container-mixins/onRenderMixin.mjs`):
сеттер регистрирует контейнер в рендер-группе (`renderGroup.addOnRender(this)`)
и кладёт функцию в `this._onRender`. Метод на прототипе подкласса **затеняет
аксессор**, сеттер не срабатывает, `_onRender` остаётся `null`, а
`RenderGroup.mjs:179` вызывает именно `container._onRender(renderer)`.

Проверено эмпирически на установленной `pixi.js@8.19.0`:

```
own onRender on M.prototype: { value: [Function: onRender], ... }
accessor on Container.prototype: true
m._onRender = null
```

Тесты этого не поймали, потому что `tests/client/parts/Map.test.js` зовёт
`bridge.onRender()` **напрямую** — проверено тело функции, но не проводка.

**Решение.** Переименовать метод и назначить его как свойство в конструкторе,
чтобы отработал сеттер:

```js
// в конструкторе, после установки _level/_levelView
if (this._level >= 1) {
  this.onRender = () => this._updateSeeThrough();
}
```

Назначать в конструкторе безопасно: `renderGroup` там ещё `null`, но
`RenderGroup.addChild` (строка 117) проверяет `child._onRender` при добавлении
на сцену и регистрирует контейнер сам.

Заодно — не вешать колбэк на слои уровня 0: сейчас `onRender` вызывался бы для
каждого статического слоя каждый кадр только чтобы выйти по первой строке.

**Тест.** В `Map.test.js` добавить проверку проводки, а не тела:
`expect(typeof bridge._onRender).toBe('function')` для уровня ≥ 1 и
`expect(bridge._onRender).toBe(null)` для уровня 0.

### 2.2 `Tank._isLocal` вычисляется в конструкторе ✅ выполнен

**Проблема.** `src/client/parts/Tank.js:95`:

```js
this._isLocal = dependencies.localPlayer?.is(context?.id) === true;
```

Это дословно тот случай, который движок отдельно запрещает в собственном
руководстве по авторингу (`vimp/docs/ai/04-client-plugin.md`, §`localPlayer`):

> **Ask at the moment you need the answer, not in the constructor.** Entities
> are created from `FIRST_SHOT_DATA`, which precedes the first binary frame —
> the local player's own part is built while `localPlayer.id` is still `null`,
> so a flag computed once in the constructor is wrong exactly for the entity
> it matters for.

То же написано в шапке `packages/engine/src/client/lib/localPlayer.js`. Если
свой танк создан из `FIRST_SHOT_DATA` (заход в комнату, пересоздание сцены
после `CLEAR`/восстановления WebGL-контекста), `_isLocal` навсегда `false` →
`levelView` не заполняется → плита не гаснет никогда.

**Решение.** Хранить не флаг, а замыкание, и спрашивать в `update`:

```js
this._isLocal = () => dependencies.localPlayer?.is(context?.id) === true;
// ...
if (this._isLocal() && this._levelView) {
  this._levelView.set(level, this.x, this.y);
}
```

**Тест.** В `tests/client/parts/Tank.test.js` — фейк `localPlayer`, у которого
`id` сначала `null`, а после первого `update` становится своим: проверить, что
`levelView.set` вызывается со второго кадра, а не «никогда».

### 2.3 `levelView` — синглтон модуля, а не клиента ✅ выполнен

`src/client/index.js:15` создаёт `const levelView = createLevelView()` на
уровне модуля, а комментарий утверждает «один экземпляр на клиента». В
браузере это совпадает, но в headless-раннере (`VirtualClient`,
`npm run sim:scenarios`) в одном процессе живёт несколько виртуальных
клиентов — состояние у них общее, и «где игрок» перезапишет тот, кто обновился
последним.

**Решение.** Создавать экземпляр внутри `hooks.services(core)` — хук зовётся
на каждое ядро:

```js
services(core) {
  const levelView = createLevelView();
  return { levelView, mapDynamics: { /* ... */ } };
}
```

Комментарий привести в соответствие. Если сервисы пересобираются чаще, чем
нужно (смена ядра), — вынести в фабрику плагина, но не в модуль.

### 3.1 Падение сквозь стены (принято: сохранять стены земли) ✅ выполнен

* `vimp-tanks/core/src/level.rs::collision_mask`:
  `Transit::Falling { .. } => STATIC_ONLY_MASK` — стены есть, тел нет.
* `core/src/client/predictor.rs`: та же маска в `tank_mask`, чтобы реплика
  собирала контакты со стенами в падении (сейчас тест
  `falling_replica_makes_no_contacts` фиксирует ровно противоположное — его
  надо переписать под новое правило, а не удалить).
* `docs/en|ru/gameplay.md`: строку «collides with nothing» заменить на
  «сталкивается только со стенами; танки, ящики, лучи и взрывы его не
  достают».

**Тесты.** В `core/tests/sim.rs`: танк падает вдоль стены → координата не
пересекает стену; танк падает в стену → приземляется перед ней.

### 3.2 Вход на рампу с верхнего конца (принято: гейт по истории входа) ✅ выполнен

**Проблема.** `step_level` (`core/src/level.rs`) считает уровень исключительно
по `ramp_at(x, y).progress`; `RampDir` задаёт лишь ориентацию прогресса и не
гейтит вход. На карте `overpass` северная рампа занимает `x 3..5, y 32..34`,
подъём на север, вершина — строка 32. Клетка `(5, 32)` достижима с земли
сбоку (клетка `(6, 32)` — обычный асфальт). Заехав в неё, танк мгновенно
получает `progress ≈ 1.0`, `z ≈ 1`, `level = 1` и следующим шагом встаёт на
плиту. Это бесплатный подъём мимо самой рампы и мимо задуманного «переходы —
направленные».

**Решение.** Запоминать конец, с которого танк зашёл на прогон, и разрешать
подъём только при входе снизу:

```rust
pub enum Transit {
    Grounded,
    Ramp { entered_at: f32 },   // progress в момент входа
    Falling { elapsed: f32, from: u8 },
}
```

В `step_level` при переходе `Grounded → Ramp` записывать `entered_at`. Далее:

* `entered_at < 0.5` — обычный подъём, `z = lerp(from, to, progress)`;
* `entered_at >= 0.5` — вход сверху: `z` держится на уровне входа
  (`state.level as f32`), уровень не меняется — прогон работает как обычная
  плоская клетка своего уровня.

Правило живёт в одном месте, поэтому клиентская реплика получает его бесплатно
(`Predictor::step` зовёт ту же `level::step_level`).

Сериализация `Transit` — `#[serde(tag = "kind")]`, добавление поля к варианту
`Ramp` ломает чтение старых дампов; отметить в `CHANGELOG.md` рядом с записью
про форму дампа `BotBrain`.

**Тесты.** `core/src/level.rs`: вход снизу поднимает; вход в клетку с
`progress > 0.5` уровня не меняет; сойти с рампы вниз по-прежнему можно.

### 3.4 Слабый отпечаток карты в `sync_levels` ✅ выполнен (вариант 1)

## Этап 4. Сегменты луча (`core/src/shot_levels.rs`) ✅ выполнен

### 4.1 Проба уровня 1 длиннее одной клетки ✅ выполнен

**Проблема.** Решение 5 плана: «в *первом* тайле с плитой, в который он вошёл,
он может поразить танк уровня 1… Дальше плита экранирует всё». Реализация
(`shot_levels.rs:149`):

```rust
let cell_span = tile * std::f32::consts::SQRT_2;
out.push(RaySegment { t0: t_slab, t1: (t_slab + cell_span).min(range), level: 1 });
```

`tile * √2` — это диагональ клетки, то есть **максимально возможный** пробег
внутри клетки при входе точно в угол. Для любого другого угла входа проба
выходит за первую клетку и накрывает вторую-третью. Комментарий утверждает,
что лишнее «отрежет проверка ближайшего попадания», но это неверно: правило
«ближайший `toi` выигрывает» выбирает минимум **между** сегментами, а не
ограничивает верхнюю границу сегмента. Танк, стоящий на второй клетке плиты,
поражается с земли — вопреки правилу.

**Решение.** Взять точную границу выхода из клетки, а не оценку. `walk_ray_cells`
уже отдаёт дистанцию входа в *следующую* клетку — достаточно не останавливать
обход на первой плите, а сделать ещё один шаг:

```rust
let mut t_slab = range;
let mut t_exit = range;
let mut slab_cell = None;

walk_ray_cells(origin, dir, range, rows, cols, tile, |cx, cy, t| {
    if slab_cell.is_some() {
        t_exit = t;          // вход в следующую клетку = выход из клетки плиты
        return false;
    }
    if !is_slab(cx, cy) { return true; }
    t_slab = t;
    slab_cell = Some((cx, cy));
    true
});
```

и `t1: t_exit.min(range)`.

**Тест.** Танк на второй клетке плиты не поражается с земли; танк на первой —
поражается; косой луч (например `[0.6, -0.8]`) даёт `t1 - t0` строго меньше
диагонали.

### 4.2 «Клетка позади» считается диагонально ✅ выполнен

`shot_levels.rs:135–141`:

```rust
let step_x: i64 = if dir[0] > 0.0 { 1 } else { -1 };
let step_y: i64 = if dir[1] > 0.0 { 1 } else { -1 };
if is_slab(cx - step_x, cy - step_y) { return out; }
```

Для осевого луча (`dir = [0, -1]`) `step_x` получает `-1`, и проверяется клетка
`(cx + 1, cy + 1)` — диагональный сосед вместо клетки строго позади. В `DDA`
такой знак безвреден (`delta` там бесконечна и `cell_x` не двигается), здесь —
нет: правило «стрелок в глубине под мостом пробу не получает» срабатывает по
чужой клетке.

Ровно этот случай — «стрелять снизу вверх из-под края моста» — основной на
карте `overpass` (респаун `team2` `spawn(49, 36, 270)` бьёт строго на север).

**Решение.** Знак нуля обрабатывать явно:

```rust
let step = |d: f32| -> i64 { if d > 0.0 { 1 } else if d < 0.0 { -1 } else { 0 } };
```

**Тест.** Вертикальный и горизонтальный лучи из-под кромки: проба есть;
из глубины под плитой: пробы нет.

### 4.3 `level_at_distance` завышает уровень для наземных целей ✅ выполнен

`level_at_distance` берёт `max` уровня среди сегментов, накрывающих `t`
(документировано). Но единственный потребитель — гейт стрельбы бота
(`bots/controller.rs`), и там это даёт ложный запрет: наземный бот **не
стреляет** в наземного врага, оказавшегося в окне пробы у кромки плиты, потому
что `level_at_distance` вернул `1`, а `target_level` = `0`.

**Решение.** Гейт формулировать через «есть ли сегмент нужного уровня на этой
дистанции», а не через «какой уровень выигрывает»:

```rust
pub fn covers_level(segments: &[RaySegment], t: f32, level: u8) -> bool {
    segments.iter().any(|s| t >= s.t0 && t <= s.t1 && s.level == level)
}
```

`level_at_distance` оставить, если нужен для отладки, но бот должен звать
`covers_level`. **Тест:** наземная цель в окне пробы — бот стреляет; цель
уровня 1 за первой клеткой плиты — не стреляет (существующий
`bot_holds_fire_through_the_slab` сохраняется).

### 4.4 Правило `endLevel` промаха не согласовано с задумкой ✅ выполнен

Отмечено самим автором в отчёте этапа 5: для промаха `endLevel` = уровень
последнего сегмента, поэтому наземный луч, прошедший мимо кромки плиты, даёт
`endLevel = 1`, и `ShotEffectController` рисует трассер и осколки на слое
моста. Хост и клиент считают это одинаково (бит-в-бит), так что рассинхрона
нет, но картинка неверная.

**Решение.** Для промаха брать уровень сегмента, действующий **в конце луча**
(`t = range`), а не последний в списке — то есть тот же `covers_level`/`max`
на `t = range`. Для наземного луча это снова `0`. Правится в двух местах
согласованно: `TanksSim::process_hitscan` (`end_level` при `hit == None`) и
`ShotPredictor::miss_level`.

## Этап 5. Клиентское предсказание ✅ выполнен

### 5.1 Фаза падения не переживает реконсиляцию ✅ выполнен

`Predictor::begin_reconcile` сбрасывает незавершённое `Falling` в `Grounded`,
а `correct_level` применяется только в `Grounded` и правит лишь `level`, но не
`z`. Значит `z` своего танка в падении определяется длиной реплея, а не
авторитетным временем падения: при скачке RTT высота дёргается, а на длинном
реплее падение может «доиграться» раньше времени.

**Решение.** Кадр `m1` уже везёт авторитетные `z` и `level`. Достаточно в
`begin_reconcile` восстанавливать фазу из кадра, а не обнулять её:

```rust
// z авторитетно ⇒ elapsed = (from - z) / from * fall_time
if authoritative_level >= 1 && authoritative_z < authoritative_level as f32 {
    self.level_state.transit = Transit::Falling {
        elapsed: fall_elapsed_from_z(authoritative_z, authoritative_level, rules),
        from: authoritative_level,
    };
    self.level_state.z = authoritative_z;
}
```

Для этого `correct_level` должен принимать пару `(z, level)` — вызов уже есть
в `client/mod.rs`, рядом читается `TANK_FIELD_LEVEL`, добавить `TANK_FIELD_Z`.

**Тест.** В `predictor.rs`: кадр с `z = 0.5, level = 1` в середине падения
восстанавливает `Falling` с соответствующим `elapsed`, а не начинает падение
заново.

### 5.2 Танк на рампе на клиенте поражается лучом не так, как на хосте ✅ выполнен

На хосте танк в `Transit::Ramp` имеет обе группы (`GROUP_1 | GROUP_2`), и его
достаёт сегмент любого уровня. На клиенте `ShotPredictor::cast_ray` фильтрует
цели по одному дискретному `tank.level` из строки кадра
(`if *id == my_id || tank.level != level { continue; }`), поэтому предсказанное
попадание по танку на рампе расходится с авторитетным.

**Решение.** Возить в `m1` не только `level`, но и признак перехода — либо
кодировать его в самом `level` (например `2` = «на рампе, обе группы»), либо
выводить на клиенте из `z`: `is_ramp = z != level as f32`. Второе бесплатно и
не трогает схему кадра:

```rust
let hits_level = tank.level == level || (tank.z - tank.level as f32).abs() > 1e-3;
```

Так же — для `MapDynamics::sim_boxes` не нужно (ящики уровень не меняют).

### 5.3 Два источника уровня у чужого танка ✅ выполнен

`ShotPredictor` фильтрует по `TankTarget.level` (из кадра), а `RemoteTanks`
отдаёт `sim_boxes()` с `PredictedBody.level` (тоже из кадра, но заполняется в
другом месте — `update` и `begin_reconcile`). Пока значения совпадают, но это
два независимых пути одного факта. Свести к одному: брать уровень из
`sim_boxes()`, когда корпус там есть, и из `TankTarget` только как запасной
(ровно как уже сделано с OBB).

### 5.4 `RemoteTanks::begin_reconcile` обходит блоки кадра дважды ✅ выполнен

Метод повторно проходит `snapshot.block_by_key(model_key)` и заново строит
`body_key(...)` только чтобы вытащить одно поле, которое `snapshot_bodies`
и так видело. Расширить `snapshot_bodies`, чтобы оно возвращало уровень рядом
с остальными полями, и убрать второй проход.

## Этап 6. Валидация карты и контракт ✅ выполнен

### 6.1 Клиент не валидирует `MAP_DATA` ✅ выполнен

`MapConfig::validate` зовётся только в `EngineSim::load_map` (хост).
`ClientMapConfig::take_levels` строит `MapLevels` из пришедшего по сети JSON
без единой проверки. Паники нет (везде `.get()`), но косой грид уровня даёт
геометрию, отличную от хостовой, и предсказание расходится молча — та самая
категория отказа, ради которой написан валидатор.

**Решение.** Вынести проверки формы (размерности гридов, `walls ⊆ floor`,
непрерывность ключей уровней) в функцию, доступную обеим сторонам, и звать её
из `TanksClient::set_map`, возвращая `Err` — `set_map` уже
`Result<(), String>`, а `main.js` логирует `[clientCore] set_map failed`.

### 6.2 Три копии одних и тех же семи проверок ✅ выполнен

Один и тот же набор правил живёт в:

* `vimp/packages/engine/core/src/map.rs::MapConfig::validate` (Rust, рантайм);
* `vimp/packages/engine/src/devtools/contract/rules/e4-map-layers.js` (JS,
  до сборки);
* `vimp-tanks/tests/config/game.test.js` (часть — руками для `overpass`).

Тексты сообщений совпадают дословно, но синхронизировать их нечем. Первый
разошедшийся случай — молчаливый.

**Решение** (по убыванию радикальности):

1. Общий корпус кейсов: JSON-фикстуры «плохих карт» в
   `vimp/packages/engine/contract/fixtures/bad-layered/*.json`, по которым
   гоняются и Rust-тест `validate`, и JS-тест правила E4, с одинаковым
   ожидаемым фрагментом сообщения. Дублирование кода остаётся, дрейф — нет.
2. `tests/config/game.test.js` в танках заменить ручные проверки `overpass`
   на прогон самого правила E4 над `gameConfig` — это и покрывает больше, и
   не расходится.

### 6.3 Не проверяются два условия, ради которых слои и делались ✅ выполнен

`validate` и E4 не ловят:

* **рампа, ведущая в пустоту** — что за верхним концом прогона есть `floor`
  уровня `to`. Молчаливый результат: танк заезжает наверх и сразу падает;
* **плита без замкнутого края** — что каждая клетка `floor` уровня N либо имеет
  соседа-`floor`, либо `wall`/край. Молчаливый результат из отчёта этапа 8:
  «стены уровня 0 танку на плите не преграда — без торцов он уезжает за
  карту». Сейчас это лечится только тем, что автор `overpass` не забыл торцы.

Обе проверки добавить в `MapConfig::validate` и в E4 (по одному кейсу на
проверку, как уже принято в `e4-map-layers.test.js`). Вторую — уровнем
`WARN`, если открытый край задуман как обрыв: тогда проверять, что за краем
есть проходимая земля.

### 6.4 `MapRadar` может тихо потерять стены ✅ выполнен

`MapRadar._draws = this._tiles.some(tile => this._solid.includes(tile))` —
слой рисует стены, только если тайл стены попал в его `layers`. У всех четырёх
существующих карт это выполняется, но правило нигде не записано: карта, где
`physicsStatic`-тайл не назван ни в одном рендер-слое, потеряет стены на
радаре без единой строки в консоли. Добавить проверку в E4 (или E2) и строку в
`docs/en|ru/extending.md`.

### 6.5 `npx vimp-contract --strict` возвращает 1 ✅ выполнен

Известно (правило `C4` не подтверждает статически сервисы `mapDynamics` /
`levelView` из `hooks.services()`). Раз плагин теперь объявляет два своих
сервиса, стоит закрыть вопрос на стороне движка: разрешить правилу C4 читать
имена из статического анализа `return { … }` в `hooks.services` или дать
плагину необязательное поле `ClientPlugin.serviceNames` — тогда `--strict`
можно вернуть в критерий готовности.

  отвечающего уровню танка в момент входа, — снизу подъём, сверху спуск,
  сбоку ничего. Уровень по дороге меняется, поэтому решение считается один
  раз, при входе, и держится до схода с прогона.
  Побочное следствие, зафиксировано тестом `bomb_dropped_over_the_void_...`:
  спавн на клетке рампы теперь считается заездом сбоку — уровень берётся из
  геометрии (0), явный уровень задаётся `set_actor_level`.
* **3.3.** Взят дешёвый вариант 1: мостовые ящики `overpass` переставлены
  из разрывов перил на крайние ряды плиты (`24, slabTop` и `64,
  slabBottom`), средний ряд оставлен свободным под сценарии. Ограничение
  записано в `plan/done/multilevel-maps/README.md` §«После первой итерации»
  и в `docs/en|ru/gameplay.md`.
* **3.4.** Взят вариант «контрольная сумма» (счётчика загрузок карты движок
  не отдаёт): `levels_checksum` — FNV-1a по гридам всех уровней, четвёртый
  элемент `levels_fingerprint`. Тест
  `second_layered_map_of_the_same_size_rebuilds_levels` в `core/tests/sim.rs`.

## Отклонения этапа 5 (записаны по правилу плана)

* **5.1.** Авторитетные `z`/`level` берутся не из `track_frame`, а из
  `TanksClient::begin_reconcile`: `track_frame` работает с
  интерполированным сэмплом, отстающим на буфер, и восстановленная по нему
  фаза падения приходила бы со сдвигом, а после приземления на хосте
  реплика ещё буфер держала бы падение. `begin_reconcile` получает СЫРОЙ
  кадр — тот самый, с позиции которого начинается реплей. Для поиска своей
  строки `TanksClient` запоминает `my_game_id` (его отдаёт `track_frame`).
  Пара кладётся в `Predictor::authoritative_level`; фазу по ней
  восстанавливает `on_server_state` (именно там жило обнуление `Falling`,
  который план называет `begin_reconcile`). Обратная к падающему `lerp`
  функция — `level::fall_elapsed`, рядом с самим правилом.
* **5.2.** Взят предложенный планом вариант «вывести признак перехода из
  `z`» (схема кадра не тронута). Побочное следствие: у падающего танка `z`
  тоже не равен `level`, поэтому клиент считает его целью обоих уровней,
  тогда как хост не даёт по нему попасть ничем (маска `STATIC_LEVEL_GROUP`).
  Различить падение и рампу по паре `(z, level)` нельзя — у обоих `z` ниже
  своего уровня. Окно — 0.35 с на танк, урон авторитетен, расходится только
  картинка трассера; лечится дискретным признаком перехода в кадре
  (вариант 1 того же пункта), если станет заметно.
* **5.4.** `snapshot_bodies` разделён: приватный `snapshot_rows` отдаёт
  `(key, ServerState, level)` за один обход кадра, а метод контракта
  подсистемы остался обёрткой над ним. Уровень пишется ДО
  `PredictedSet::begin_reconcile` (тот уровень не читает), поэтому строки
  ключей переезжают в `entries` без клонирования.
