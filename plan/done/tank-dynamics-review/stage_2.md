# Этап 2. Ядро: валидация `landingShake` и чистка после этапа 1 ✅ выполнен

Чисто качественный этап: поведение игры не меняется ни на йоту, меняются
надёжность конфига и читаемость `level.rs`. Делается ПОСЛЕ этапа 1 —
`step_layered` там правится, и вынос полёта в отдельную функцию поверх уже
правленого кода дешевле, чем наоборот.

## 2.1. `LandingShake` не проходит валидацию

`core/src/config.rs:79` объявляет структуру, `TanksConfig::validate()`
(строка 304) её не проверяет вовсе. Последствия:

- `intensity`/`duration` отрицательные — тряска камеры с отрицательной
  интенсивностью уезжает в движок как есть;
- `fullImpact <= minImpact` — `push_landing_shake`
  (`core/src/tanks.rs:908`) молча выходит по `if span <= 0.0 { return; }`,
  то есть опечатка в конфиге выключает тряску без единого слова. Это ровно
  тот класс расхождений, который остальной `validate()` ловит.

**Решение.** В `TanksConfig::validate()`, после блока `tilt_max`:

```rust
        if let Some(shake) = &self.levels.landing_shake {
            if shake.intensity < 0.0 {
                return Err(format!(
                    "levels.landingShake.intensity must be >= 0, got {}",
                    shake.intensity
                ));
            }

            if shake.duration <= 0.0 {
                return Err(format!(
                    "levels.landingShake.duration must be > 0, got {}",
                    shake.duration
                ));
            }

            if shake.min_impact < 0.0 {
                return Err(format!(
                    "levels.landingShake.minImpact must be >= 0, got {}",
                    shake.min_impact
                ));
            }

            // равенство порогов — не «тряски нет», а опечатка: выключается
            // тряска отсутствием блока целиком
            if shake.full_impact <= shake.min_impact {
                return Err(format!(
                    "levels.landingShake.fullImpact ({}) must be > minImpact ({})",
                    shake.full_impact, shake.min_impact
                ));
            }
        }
```

После этого страховка `if span <= 0.0 { return; }` в
`TanksSim::push_landing_shake` становится недостижимой на валидном
конфиге. Оставить её (реплика и сетевые данные строятся мимо `validate`),
но заменить комментарий на:

```rust
        // страховка на случай конфига, не прошедшего `validate()`
        // (реплика строится из сетевых данных): деления на ноль быть не
        // должно ни при каких входных данных
```

**Тесты** (`core/src/config.rs`, модуль `tests`, по образцу
`validate_rejects_cap_below_fall_damage`): четыре теста — отрицательная
интенсивность, нулевая длительность, отрицательный `minImpact`,
`fullImpact == minImpact`. Плюс один положительный:
`validate_accepts_a_config_without_landing_shake` (поле `Option`, `None`
обязан проходить).

## 2.2. Литерал `1e-3` вместо `LEVEL_EPSILON`

`core/src/level.rs:644`, внутри `entry_is_legal`:

```rust
        if (state.z - state.level as f32).abs() > 1e-3
```

В том же файле, строка 256, объявлена
`pub const LEVEL_EPSILON: f32 = 1e-3` ровно с этим смыслом («высота ровно
на своём уровне») и с комментарием «Число одно на всех, кто задаёт этот
вопрос, — иначе две копии правила разойдутся молча». Здесь задаётся именно
этот вопрос.

**Решение.** Заменить на `LEVEL_EPSILON`. Поведение не меняется —
константа равна тому же литералу. Отдельного теста не нужно: существующие
тесты гейта рампы (`entry_*` в модуле `tests` того же файла) покрывают
ветку.

## 2.3. Неиспользуемый параметр `_impact`

`core/src/tanks.rs:937`:

```rust
fn apply_fall_damage(&mut self, ctx: &mut SimCtx, game_id: u32, height: f32, _impact: f32)
```

`_impact` не используется. Он появился, когда урон и тряска считались
одной функцией; теперь тряска живёт в `push_landing_shake`, которая
получает `impact` сама.

**Решение.** Убрать параметр из сигнатуры и из вызова (строка 899):
`self.apply_fall_damage(ctx, id, height);`. Кортеж `landed` продолжает
нести оба числа — `impact` нужен `push_landing_shake`.

## 2.4. Полёт — 70-строчный блок внутри `step_layered`

`core/src/level.rs`, `step_layered` начинается с
`if let Transit::Airborne { vz, from, to, peak } = state.transit { … }` —
это ~70 строк с интегрированием, выбором цели, проверкой пересечения
уровня сверху и приземлением. Остальная функция (рампа, вылет, срыв) —
ещё столько же. Функция делает три разных дела, и правка одного требует
чтения всех трёх.

**Решение.** Вынести тело ветки в отдельную функцию того же модуля, не
меняя ни одной формулы:

```rust
// Шаг тела в полёте: интегрирование дуги, выбор клетки касания и
// приземление. Отдельная функция, потому что `step_layered` иначе держит
// три независимых правила подряд (полёт, прогон рампы, сход с плиты).
// Возвращает событие; состояние правится на месте.
fn step_airborne(
    state: &mut LevelState,
    x: f32,
    y: f32,
    vz: f32,
    from: u8,
    to: u8,
    peak: f32,
    levels: &MapLevels,
    rules: &LevelRules,
    dt: f32,
) -> LevelEvent {
    // …тело существующей ветки без изменений…
}
```

В `step_layered` остаётся:

```rust
    if let Transit::Airborne { vz, from, to, peak } = state.transit {
        return step_airborne(state, x, y, vz, from, to, peak, levels, rules, dt);
    }
```

Функция получает `#[allow(clippy::too_many_arguments)]` — как и соседние.

**Тесты.** Новых не нужно: ветка уже покрыта тестами
`level.rs` (длительность падения, ускорение параболы, прыжок на свой
уровень, перелёт стен) и `core/tests/sim.rs`. Зелёный прогон после выноса
— и есть доказательство, что формулы не тронуты.

## 2.5. `fall_speed_at` — мёртвый код

Проверено при ревью:

```
core/src/level.rs:189   объявление (pub fn fall_speed_at)
core/src/level.rs:349   упоминание в комментарии
core/src/level.rs:1595…1602  единственный потребитель — её собственный тест
```

Боевых вызовов нет. Функция появилась в этапе 1 исходной задачи как способ
восстановить фазу полёта у реплики по высоте кадра, но этап 3 провёл `vz`
через кадр напрямую (`Predictor::correct_level` берёт скорость из кадра) —
и обратная функция осталась не у дел. `pub` без потребителей вводит в
заблуждение: читатель считает, что реплика ей пользуется.

**Решение.** Удалить `fall_speed_at` вместе с её тестом
(`core/src/level.rs`, тест на длительность/скорость падения — удалить
только те утверждения, что зовут `fall_speed_at`, остальные оставить).
Комментарий на строке 349 переписать так, чтобы он объяснял, зачем
трапеция, не ссылаясь на удалённую функцию:

```rust
        // трапеция (скорость усредняется по шагу) — это ТОЧНАЯ выборка
        // параболы в моменты `n·dt`, а не приближение: v² = v0² − 2g·Δz
        // держится на каждом шаге. Реплика берёт `vz` из кадра и обязана
        // попадать в те же моменты: с полушаговой схемой её падение
        // кончалось тиком раньше хостового, и газ расходился на каждом
        // падении
```

Упоминания `fall_speed_at` в `docs/en/core.md` и `docs/ru/core.md` убрать
на этапе 7 (правка документации собрана там).

**Перед удалением** обязательно перепроверить командой
`grep -rn "fall_speed_at" core src docs` — если этап 3 или 4 этого плана
успел завести нового потребителя, шаг отменяется.
