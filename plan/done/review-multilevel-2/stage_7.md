### 7.0.1 Нав-граф ботов не знает о стражах прогона рампы ✅ движковая часть выполнена

**Симптом.** В танках (`/Users/dmitry/Sites/my/vimp-tanks`) тест
`scripted_bot_drives_onto_the_bridge` (`core/tests/sim.rs`) помечен
`#[ignore]` и падает при снятии метки: бот, заспавненный на земле, за 60
секунд ни разу не заезжает на мост слоёной карты. Воспроизведение:

```bash
cd /Users/dmitry/Sites/my/vimp-tanks
cargo test --manifest-path core/Cargo.toml --test sim \
  scripted_bot_drives_onto_the_bridge -- --ignored --nocapture
```

Бот при этом жив и ездит: в отладочной распечатке он крутится около
`x≈326…460, y≈220…330` (карта фикстуры — 20×20 клеток по 32), то есть у
ВЕРХНЕГО торца прогона рампы, и уровень остаётся 0.

**Причина.** В итерации 2 движок получил «стражи прогона»
(`GameMap::create_ramp_guards`, `packages/engine/core/src/map.rs:1384`) —
три тонких статических коллайдера на каждый прогон рампы: два борта вдоль
прогона и один поперёк «неправильного» (дальнего по ходу подъёма) торца.
Они стоят в отдельной группе `RAMP_GUARD_GROUP` (`map.rs:647`) и
существуют только для тел уровня `low = min(run.from, run.to)`
(`ramp_guard_interaction`, `map.rs:685`); законно поднимающееся тело
проходит их насквозь (`levels_interaction_on_ramp`, `map.rs:678`).
Смысл — закрыть заезд на клин сбоку и под клин с верхнего торца.

Нав-граф про них не знает. `NavigationSystem::generate_layered`
(`packages/engine/core/src/nav/navigation.rs:135`) строит сетку
проходимости уровня 0 ровно из списка сплошных тайлов:

```rust
nav.nav_grid = grid0
    .iter()
    .map(|row| {
        row.iter()
            .map(|tile| u8::from(levels.solid(0).contains(tile)))
            .collect()
    })
    .collect();
```

Тайл рампы сплошным не является, поэтому клетки прогона остаются
проходимыми, узлы графа в них ставятся, и путь на мост прокладывается
через них — в том числе поперёк прогона и через закрытый верхний торец.
Бот упирается в невидимую для него преграду, через 1.5 с ловит
`stuck_timer` и уходит в `ClearingObstacle`
(`vimp-tanks/core/src/bots/controller.rs:233`) — стреляет в препятствие,
потом строит тот же путь заново. Цикл не размыкается.

**Правка.** Клетки прогона обязаны стать НЕпроходимыми для уровня, с
которого прогон начинается.

1. В `generate_layered` после сборки `nav_grid` (уровень 0) и
   `upper_grids` (индекс 0 = уровень 1) пройти прогоны
   `levels.runs()` (`map.rs:984`, элементы — `RampRun` с полями
   `axis`, `sign`, `from`, `to`, `min`, `max`, `cross_min`, `cross_max`;
   границы в МИРОВЫХ единицах, `map.rs:716-730`) и пометить клетки
   каждого прогона в сетке уровня `low = min(from, to)`.
   Принадлежность клетки прогону проще всего брать готовой функцией
   `MapLevels::ramp_at(x, y)` (`map.rs:1066`) по центру клетки
   (`(cx + 0.5) * tile_size`), она отдаёт `RampSample` с номером прогона
   `run`; заводить публичный доступ к приватному `run_cells`
   (`map.rs:746`) не обязательно.
2. **Метка обязана быть отдельным значением, а не «стеной».** Сетка одна
   на два вопроса: `is_walkable_on` (`navigation.rs:400`) считает клетку
   проходимой при `cell == 0`, а `has_obstacle_between_on`
   (`navigation.rs:428`) считает препятствием `cell == 1`. Если пометить
   прогон единицей, он станет ещё и непрострельным/непросматриваемым —
   боты перестанут видеть друг друга сквозь рампу (`controller.rs:284`,
   `controller.rs:570`). Поэтому значение — `2`: «непроходимо, но не
   препятствие для луча». Оба метода уже сравнивают с конкретными
   константами, менять их не нужно; в комментарии к полю `nav_grid`
   описать третье значение.
3. Ребро рампы не ломается и правки не требует: `connect_ramps`
   (`navigation.rs:251`) ставит обе точки ЗА кромками прогона
   (`run.min - half` / `run.max + half`), а сам клин бот проезжает как
   обычный отрезок пути между этими узлами.
4. Верхний уровень не трогать: плиты уровня `high` в клетках прогона нет,
   и в `upper_grids` они и так непроходимы.

**Тесты движка** (`navigation.rs`, модуль `tests`, фикстура
`layered(with_ramp: bool)` около строки 665):

- новый: на слоёной карте с рампой `is_walkable_on(low, центр клетки
  прогона)` == `false`, а `has_obstacle_between_on(low, …)` сквозь
  прогон == `false` (луч проходит);
- существующие `ramp_edge_connects_levels` и
  `no_path_between_levels_without_ramp` — остаются зелёными;
- путь с земли на плиту по-прежнему находится (`find_path_on`).

**Документация E:** страница о навигации/ботах — про третье значение
сетки и про то, что клетки прогона проходимы только через ребро рампы.
**Журнал E:** `### Fixed`.

**Что сделать в танках после публикации:**

1. `core/Cargo.toml` → `vimp-engine-core = "0.13.1"` (или `0.14.0`),
   `package.json` → `"vimp-engine": "^0.32.1"`,
   `npm install`.

### 7.0.2 Реплика собирает стены карты поклеточно, хост — склеенными блоками ✅ движковая часть выполнена

**Симптом.** `npm run sim:scenarios` в танках: 4 сценария из 12
(`bridge.json`, `crosslevel.json`, `fall.json`, `terraces_climb.json`)
валят контракт `predictionDrift` — каждый по ОДНОЙ реконсиляции из ~350,
поля `angle` (Δ 0.21 при пороге 0.06) и `angvel` (Δ 2.81 при пороге 1.5).
Воспроизведение:

```bash
cd /Users/dmitry/Sites/my/vimp-tanks
npm run sim -- --scenario tests/scenarios/bridge.json
# запись: serverTime 1700000003500, authoritative [73.27, 394.18, 0.212,
# 12.39, -18.25, 2.806, 0, 1]
```

**Причина.** Разобрана по шагам инструментацией обеих сторон. До контакта
хост и реплика идентичны: `x=72.61 y=395.07 v=(148.85, 0.87)`, уровень 1,
`Grounded`, `prev_cell (5, 30)`. Следующий шаг:

| | результат шага | контакт |
| --- | --- | --- |
| хост | `x=72.93 y=394.80 v=(7.29, -40.45) w=5.521` | `Group(GROUP_2 \| GROUP_9)` в `(345.6, 403.2)`, полуразмеры `(268.8, 6.4)` |
| реплика | `x=72.81 y=395.08 v=(-7.65, -0.04) w=0.000` | нормаль `(1.0, 0.006)`, глубина `1.106` |

Бьются об одну и ту же стену — перила уровня 1 в строке 31 карты
`overpass`, — но видят её РАЗНОЙ геометрией:

- хост склеивает соседние сплошные тайлы в прямоугольные блоки
  (`GameMap::create_static` → `search_static_block`,
  `packages/engine/core/src/map.rs:1331` и `:1658`): здесь это одно тело
  шириной 537.6 (x 76.8…614.4, y 396.8…409.6);
- реплика собирает контакты ПОКЛЕТОЧНО
  (`client::collision::collect_tile_contacts`,
  `packages/engine/core/src/client/collision.rs:178`), тайл 12.8.

Танк входит в юго-западный угол этой стены по касательной: перекрытие по
x — 1.11, по y — 1.27. Rapier на длинном блоке разрешает контакт по оси Y
(отбрасывает танк вдоль стены на север и даёт вращение `w = 5.5`), а
реплика на отдельном тайле берёт минимальную ось X и отбрасывает танк
назад на запад без вращения. Дальше траектории расходятся, и детектор
ловит `angle`/`angvel` на ближайшем кадре.

Расхождение не новое (база этапа 0: максимум по `angvel` 0.98), но
безразмерный уклон этапа 2/3 разогнал танк на выезде с рампы до 148 ед/с,
и касательный удар об угол стал жёстким. Проверено, что дело НЕ в уровнях,
масках, стражах прогона, вердикте гейта, откате `LevelState` и новых
константах подъёма — каждое откатывалось по отдельности, расхождение
оставалось.

**Правка.** Склеенные блоки строятся ОДИН раз и отдаются обеим сторонам.

1. В `MapLevels` (`map.rs:737`) добавить список блоков по уровням —
   например `static_blocks: Vec<Vec<StaticBlock>>`, где
   `StaticBlock { x, y, half_w, half_h }` в мировых единицах, — и считать
   его в `MapLevels::build` тем же жадным алгоритмом
   `search_static_block`. Публичный доступ: `static_blocks(level: u8)`.
2. `GameMap::create_static` перестаёт склеивать сама и ставит коллайдеры
   по этому списку. Порядок вставки тел обязан остаться прежним
   (одноуровневая карта — бит в бит), иначе поедут дампы и индексы
   `static_bodies`/`static_levels`.
3. Для реплики добавить функцию контактов по блокам (например
   `collect_block_contacts(obb: &Box2, blocks: &[StaticBlock])
   -> Vec<TileContact>`) рядом с `collect_tile_contacts`. Старую функцию
   либо оставить (её зовут только тесты и танки), либо удалить вместе с
   переводом танков — тогда это минор, а не патч.
4. В танках (`core/src/client/predictor.rs`, цикл стен в `resolve_world`,
   ~строки 906-950) заменить `collect_tile_contacts(&obb, grid,
   levels.solid(level), levels.tile_size())` на обход блоков уровня.
   Фильтр по маске уровня (`mask.intersects(level_group(level) |
   STATIC_LEVEL_GROUP)`) и зеркало стражей прогона, которое стоит рядом,
   не трогать.

**Тесты движка:** склейка блоков даёт те же прямоугольники, что хостовые
коллайдеры (сравнение с `create_static` на фикстуре); контакт OBB с
длинным блоком выбирает ту же ось, что Rapier, на касательном ударе об
угол (регрессия ровно на разобранный случай: перекрытие 1.11 по x против
1.27 по y).

**Критерий приёмки в танках:** `npm run sim:scenarios` — 12 зелёных,
пороги `divergence.thresholds` в `tests/scenarios/*.json` НЕ трогать;
дрейф `bridge.json` не хуже базы этапа 0
(`[2.236, 0.9264, 0.0328, 6.6667, 8.6313, 0.9773, 0, 0.0208]`,
0 нарушений).

### 7.0.3 Стражи прогона огораживают ПОЛОСЫ широкой горки ✅ движковая часть выполнена

**Симптом.** На `overpass` (`rampNorth` — блок 3 × 3, `src/data/maps/
overpass.js:34`) танк не заезжает на горку с подножия: он упирается в
невидимую преграду ещё до кромки. Воспроизведение — тест реплики в танках:

```bash
cd /Users/dmitry/Sites/my/vimp-tanks
cargo test --manifest-path core/Cargo.toml --lib \
  replica_drives_onto_a_wide_ramp_off_centre -- --ignored --nocapture
# танк упёрся во внутренний борт блока: x = 72.95 (кромка рампы — 80)
```

Тест едет ровно по границе двух полос; заезд по центру полосы
(`replica_drives_onto_a_wide_ramp`, зелёный) проходит. То есть широкая
горка проезжается только при попадании корпусом строго внутрь одной
полосы, а обычная езда с поворотом почти всегда идёт по границе.

**Причина.** `MapLevels::build_runs` режет прямоугольный блок тайлов рампы
на N параллельных полос-прогонов (по прогону на строку при оси x и на
колонку при оси y). `GameMap::create_ramp_guards`
(`packages/engine/core/src/map.rs:1384-1441`) ставит КАЖДОМУ прогону два
борта — по `run.cross_min` и по `run.cross_max`, длиной во весь прогон
(`half_main = (run.max - run.min) / 2`). У широкого блока внутренние
границы полос общие, и на каждой встают сразу два таких борта: блок
превращается в набор жёлобов шириной в тайл, стенки которых доходят до
самой линии входа. Стражи снимаются только с законно поднимающегося
(`body_filter`, `map.rs:649`), а до входа танк ещё не поднимается — он и
упирается. Корпус (6 мировых единиц) уже тайла (12.8), но по границе он
лежит в обоих жёлобах сразу.

Правило «полосы одной широкой горки — одна горка» в игре уже есть
(`is_lane_change`, `vimp-tanks/core/src/level.rs`): вердикт гейта
переносится между полосами с той же осью, знаком, перепадом и границами
вдоль оси. Физика обязана отвечать той же геометрии.

**Правка (E).**

1. В `create_ramp_guards` группировать прогоны в БЛОКИ по признаку
   `is_lane_change`: одинаковые `axis`, `sign`, `from`, `to`, `min`, `max`
   и смежные интервалы поперёк (`cross_max` одного равен `cross_min`
   следующего). Борта ставить только по ВНЕШНИМ поперечным границам блока,
   торцевой страж — один на блок, во всю его ширину
   (`half_cross` блока), а не по прогону.
2. Признак блока обязан быть ОДИН на движок и игру. Лучше отдать его
   крейтом — например `RampRun.block: u16` (номер блока, проставляется в
   `build_runs`) плюс уже публичные поля; тогда `is_lane_change` в танках
   сводится к `a.block == b.block`, а расхождения двух определений
   становятся невозможными. Новое публичное поле — это минор
   (крейт `0.14.0`), как и 7.0.2.
3. Заезд СБОКУ на блок и въезд под клин с верхнего торца обязаны остаться
   закрытыми: внешние борта и торец блока никуда не деваются.

**Тесты движка** (`map.rs`, рядом с
`ramp_guard_blocks_a_body_of_the_lower_level_from_the_side:2263`):
фикстура с блоком 3 × 2 (широкая рампа) — стражей у блока ровно 3
(два внешних борта и торец), а не 9; тело, едущее по внутренней границе
полос с подножия, доезжает до вершины; тело, заезжающее сбоку, по-прежнему
упирается.

**Что сделать в танках после публикации:**

1. Зеркало стражей в реплике (`core/src/client/predictor.rs`,
   `resolve_world`, ~строки 955-1020) собрать по тем же блокам.
2. `is_lane_change` (`core/src/level.rs`) перевести на `block` прогона.
3. Снять `#[ignore]` с `replica_drives_onto_a_wide_ramp_off_centre`
   (`core/src/client/predictor.rs`) — тест обязан позеленеть.
4. Проверить глазами на `overpass`: заезд на широкую горку с поворотом.

«контакт OBB с длинным блоком выбирает ту же ось, что Rapier, на касательном
ударе об угол». Проверка `parry::query::contact` на разобранной геометрии
показала, что на этой позе Rapier выбирает ось **x** и для склеенного блока
(нормаль `(1, 0)`, глубина `1.10599`), и для одиночного тайла: у блока и у
углового тайла общие рёбра `x = 76.8` и `y = 396.8`, поэтому одной геометрией
выбор оси не объясняется — на хосте расходились поза и скорость тела, а не
форма стены. Вместо непроверяемого утверждения записаны два факта, которые
действительно держат правку: (1) `collect_block_contacts` на разобранном
случае воспроизводит нормаль и глубину Rapier для хостового коллайдера и
даёт РОВНО один контакт с плечом в центре тела хоста; (2) корпус на длинной
стене получает у поклеточного сбора два контакта там, где у хоста один, —
разные плечи и есть источник расхождения по `angle`/`angvel`.

### Что выяснилось при исполнении танковой части

**7.0.1 потребовал ещё двух правок сверх плана — обе сделаны.** Снятия
`#[ignore]` не хватило: бот по-прежнему не заезжал на мост.

1. *Движок.* `connect_ramps` брала ближайшие узлы общей сетки, а её шаг —
   два тайла: на фикстуре моста путь шёл `(160, 288) → (352, 288)`, то есть
   ровно по борту прогона (`cross_min = 288`), где стоит страж. Теперь у
   прогона свои узлы по центру полосы (`add_node`/`link`), и путь идёт
   `(176, 304) → (336, 304)`. Тест
   `ramp_edge_runs_through_the_middle_of_the_run`.
2. *Танки.* Лучи объезда препятствий (`bots/controller.rs::avoid_obstacles`)
   ходили с фильтром `level_interaction(my_level)`, который стражей ВИДИТ:
   прогон шириной в тайл — коридор, и боковые лучи упирались в его борта на
   каждом подъезде, разворачивая бота от подножия. Фильтр заменён на
   `levels_interaction_on_ramp(level_group(my_level))` — стражи лучам не
   видны; заезд сбоку держат сами стражи и нав-граф, который через клетки
   прогона путь не прокладывает.

После этих двух правок `scripted_bot_drives_onto_the_bridge` зелёный
(бот наверху на 1.0 с), `#[ignore]` снят.

**7.0.3 — снятия `#[ignore]` хватило.** `replica_drives_onto_a_wide_ramp_off_centre`
зелёный после перевода реплики на стражей по блокам и `is_lane_change` на
`RampRun::block`.

**7.0.2 — правка сделана, но дрейф она НЕ чинит.** Реплика переведена на
`collect_block_contacts` по `levels.static_blocks(level)`, геометрия стен у
хоста и реплики теперь одна. `npm run sim:scenarios` при этом даёт
РОВНО ту же картину, что и до правки: те же 4 сценария, те же числа
(`bridge`/`fall`: 1 нарушение, `angle` 0.2063, `angvel` 2.8059;
`crosslevel`: 2; `terraces_climb`: 24 нарушения по `x`/`vx`/уровню — это
другой, свой дефект, он и на базе выглядел так же).

Причина, по которой гипотеза этапа не сработала, проверена прямым замером
`parry::query::contact`: на разобранной позе и склеенный блок, и одиночный
угловой тайл дают ОДНУ ось (нормаль `(1, 0)`, глубина `1.106`) — у блока и
у углового тайла общие рёбра `x = 76.8` и `y = 396.8`. Значит выбор оси на
хосте определяется не формой стены, а тем, чего у реплики нет вовсе:
предиктивными контактами Rapier (`soft_ccd_prediction(6)` на корпусе танка,
`core/src/tank.rs:167`), многоточечным манифольдом и позой тела внутри шага.
Реплика собирает контакт по факту перекрытия текущего OBB и разрешает его
одним вектором минимального выталкивания.

Правка при этом не лишняя: она убрала реальное расхождение (корпус на
длинной стене получал у реплики несколько контактов с разными плечами там,
где у хоста один) и стоит в журнале как `Fixed`. Но критерий «12 зелёных
сценариев» ею не закрывается — нужен отдельный разбор предиктивных
контактов в реплике. Это решение за пользователем: чинить сейчас
(подэтап 7.0.4) или закрывать этап 7 без него.
