## 4.0 Ключевое наблюдение: параллакс — это масштаб вокруг камеры

`MapVolume._updateSlices` (`src/client/parts/MapVolume.js:181-194`) двигает
каждую вершину:

```js
positions[i]     = base[i]     + (base[i]     - camX) * k;
positions[i + 1] = base[i + 1] + (base[i + 1] - camY) * k;
```

Это алгебраически тождественно **однородному масштабу вокруг точки камеры**:

```
p' = cam + (p - cam) * (1 + k)
   = p * (1 + k) - cam * k
```

То есть тот же результат даёт трансформ контейнера:

```js
container.scale.set(baseScale * (1 + k));
container.position.set(-camX * k * baseScale, -camY * k * baseScale);
```

(координаты камеры — в мировых единицах, `baseScale` — `data.scale` карты).

Следствия:

- перезапись 40 000 float'ов и четыре `bufferData` на каждый кадр движения
  (замер: `overpass` 81 × 61 вершин × 2 × 4 среза) заменяются на четыре
  присваивания трансформа;
- та же формула поднимает **весь слой уровня N**, и для этого не нужен меш —
  достаточно обычного спрайта запечённого слоя;
- формула становится одна на всех: слой, объём, тень, тело.

Именно поэтому этап начинается с общего модуля.

## 4.1 Общий модуль параллакса

Создать `src/client/parallax.js`:

```js
// Проекция 2.5D: объект на высоте z рисуется смещённым ОТ центра камеры —
// чем выше и чем дальше от центра экрана, тем сильнее. Ровно так читается
// высота в GTA 2. Формула одна на всех потребителей:
//
//   точка:     p' = p + (p - cam) * k
//   контейнер: тот же результат даёт масштаб (1 + k) вокруг центра камеры
//
// k = высота в уровнях * shear. Разные знаки у разных потребителей — самая
// частая ошибка этой проекции: смещается ОБЪЕКТ, а его тень остаётся в
// мировой точке (см. Tank._updateShadow).

export function offsetPoint(x, y, camera, k) { ... }         // -> {x, y}
export function applyParallax(container, camera, k, baseScale) { ... }
```

Единственный источник `shear` — `src/config/render.js` (см. 4.5).

Потребители: `Map` (слой уровня N), `MapVolume` (срезы), `Tank` (корпус и
тень), `Map` (динамическое тело по его `z`), `Smoke`, `Bomb`, эффекты.
Формулу больше нигде не писать.

**Тест:** `tests/client/parallax.test.js` — тождество «точечная формула и
трансформ контейнера дают одну и ту же мировую точку».

## 4.2 Слой уровня N поднимается над землёй (Д5, жалоба 1)

### Проблема

`src/client/parts/Map.js:92`:

```js
this.zIndex = levelZ(Number(data.layer) || 1, this._level);
```

— и всё. Плита моста и его перила рисуются ровно в тех же экранных
координатах, что и асфальт под ними, отличаясь только порядком отрисовки.
Игрок видит «стены моста на уровне 0» — глухую стену поперёк проезда.

### Правка

В `Map`, ветка `static`, при `this._level >= 1`:

```js
// слой уровня N висит над землёй: его сдвиг от центра камеры — тот же
// параллакс, что у объёмов и у танков (src/client/parallax.js)
this._parallaxK = this._level * cfg.shear;
```

и в уже существующем колбэке `onRender` (`Map.js:106`) звать
`applyParallax(this, camera, this._parallaxK, this._baseScale)` рядом с
`_updateSeeThrough()`. Базовый масштаб (`data.scale`) сохранить в поле, так
как `this.scale` теперь пересчитывается каждый кадр.

Уровень 0 не трогать вовсе: `k = 0` даёт тождественный трансформ, но лишний
пересчёт на каждый кадр ни к чему.

### Что обязано поехать следом

- **Центр дыры** (`Map._updateHole`, `:246-253`) считается из позиции игрока
  в мировых координатах. Игрок теперь тоже смещён своим `z`, поэтому центр
  брать из смещённой точки: `offsetPoint(view.x, view.y, camera, view.z *
  shear)`, затем в экранные пиксели прежним умножением на трансформ сцены.
  Иначе дыра поедет относительно танка тем сильнее, чем дальше игрок от
  центра экрана.
- **Тела на слое** (ящики): `Map._updateDynamicSeeThrough` дополнительно
  смещает `this.position` по своему `_level`/`z`, иначе ящик поедет
  относительно плиты, на которой стоит.
- **Танк, дым, следы, бомба, эффекты** — то же смещение по своему `z`
  (см. 4.4).
- **Радар** (`MapRadar`, `TankRadar`) параллакс **не** получает: это схема,
  а не сцена.

## 4.3 Объёмы участвуют в see-through (Д4, жалобы 1 и 2)

### Проблема

`src/config/client.js:171-181` объявляет `levelView` зависимостью
`MapVolume`, но парт его ни разу не читает (`grep levelView
src/client/parts/MapVolume.js` — ноль совпадений). Плоский слой перил
пробивается «дырой» вокруг игрока, а его экструзия остаётся глухой: игрок
под мостом видит дыру в плите и сплошной блок перил поверх неё.

### Решение — слить `MapVolume` в `Map`

Рекомендуемый путь (принять решение в начале этапа и записать в отклонениях):

1. `Map` для слоя с `data.volume > 0` строит K дополнительных спрайтов из
   **той же** запечённой текстуры (сейчас слой печётся дважды — Д16), кладёт
   их детьми в тот же контейнер под основным спрайтом и каждому даёт свой
   трансформ параллакса `k = (level + volume * i / K) * shear`.
2. Прозрачность и фильтр «дыры» тогда применяются к контейнеру целиком —
   и к плоскому слою, и к его объёму, одним проходом фильтра.
3. `MapVolume` удаляется: из `src/client/parts/index.js`, из `gameSets`,
   `entitiesOnCanvas`, `componentDependencies` (`src/config/client.js:13-14,
   23, 157, 160, 174`), из тестов.

Что это чинит разом: Д4 (объём гаснет), Д16 (двойное запекание, K лишних
мешей, течь геометрии, пустые контейнеры `MapVolume` на каждое динамическое
тело), плюс снимает второй проход фильтра на слой.

**Запасной путь**, если слияние окажется рискованным (порядок отрисовки
внутри контейнера, поведение фильтра на детях): оставить `MapVolume`
отдельным партом, но научить его читать `levelView` — alpha в режиме
`'layer'`, собственный фильтр «дыры» в режиме `'hole'`, — и брать текстуру
слоя из общего кеша, чтобы не печь второй раз. Причину отказа от слияния
записать.

### Порядок отрисовки

Срезы объёма обязаны лежать между своим плоским слоем и слоем выше:
`zIndex` слоя + доля (сейчас `+ 0.5`, `MapVolume.js:68`). При слиянии
порядок задаётся порядком детей — проверить, что перила уровня 1 по-прежнему
рисуются поверх танка на плите, а плита — под ним (`layers: { 1: [slab],
4: [railing] }` в `overpass.js:175-178`).

## 4.4 Тень остаётся на земле, смещается корпус (Д6)

`src/client/parts/Tank.js:370-379`:

```js
const camera = cameraCenter(this.parent, this._renderer);
const shear = SHADOW_SHEAR * this._z;

shadow.x = camera ? this.x + (this.x - camera.x) * shear : this.x;
shadow.y = camera ? this.y + (this.y - camera.y) * shear : this.y;
```

Смещается **тень**, а корпус стоит в мировой точке — проекция вывернута
наизнанку: тень выглядит выше танка. `MapVolume` при этом двигает верхние
срезы правильно, то есть два места в одном рендере противоречат друг другу.

Правка:

- корпус (`this.position`) смещается на `offsetPoint(x, y, camera, z *
  shear)`;
- тень рисуется в **немодифицированной** мировой точке `(this.x, this.y)`;
- масштаб и alpha тени остаются как есть (растёт и бледнеет с высотой);
- `shadow.zIndex = levelZ(TANK_BASE_Z - 1, Math.floor(this._z))` сохранить —
  тень лежит на слое, НАД которым висит танк.

Внимание: `this.x`/`this.y` — это ещё и точка, которую танк пишет в
`levelView` (`Tank.js:298-300`), и позиция звука (`_getSoundData`). Туда
обязана уходить **мировая, несмещённая** точка, иначе поедут и дыра, и
панорама. Смещение накладывать только на отрисовку: хранить мировые
координаты в полях (`this._worldX/_worldY`) и писать в `this.position` уже
смещённые — как это сделано у динамики `Map` (`Map.js:124-125`).

## 4.5 Клин рампы (визуальная половина жалобы 3)

### Что должно получиться

Горка — не плоский спрайт, а клин с нарастающей высотой: у подножия высота 0,
у верхнего торца — `to − from` уровней. Тогда танк, едущий под клином (у
терраса `rampSide`), скрыт за ним, а сбоку клин читается как препятствие —
что теперь и физически верно (стражи из этапа 2.2).

### Реализация

Прогон — прямоугольник, вытянутый вдоль оси. Значит клип по прямоугольнику
достаточно, меш не нужен:

1. Из контекста парта (этап 2.5) взять описание прогонов уровня.
2. Запечь отдельную текстуру только из клеток рампы (тот же
   `bakeTileLayer`, список тайлов — тайлы рамп слоя).
3. Для среза `i` из `K` показать **верхнюю часть** прогона, где
   `progress >= i / K`: это подпрямоугольник, задаваемый `texture.frame`
   (не новая текстура — кадр существующей). Каждому срезу — свой трансформ
   параллакса `k = (level + (to - from) * i / K) * shear`.
4. Нижние срезы тонируются `volume.sideTint` (боковые грани), верхний —
   чистый.

Стоимость — `K` спрайтов на прогон, без пересчёта вершин.

Тонкость: у прогонов разных направлений «верх» — разная сторона
прямоугольника; знак берётся из `dir`/`sign` прогона. Тест на все четыре
направления обязателен.

### Альтернатива

Если клип кадром окажется неудобен (например, прогон не выровнен по границам
тайлов текстуры), строить меш с высотой вершины по прогрессу — как сейчас в
`MapVolume`, но только над клетками прогона. Дороже, но общее решение.

### Отклонения от плана и их причины

1. **Слияние состоялось** (рекомендованный путь 4.3). Запасной путь не
   понадобился: порядок отрисовки внутри контейнера задаётся порядком
   детей, а фильтр «дыры» на контейнере накрывает и слой, и его срезы.
2. **Срезы лежат НАД плоским спрайтом**, а не под ним (4.3 п. 1 говорил
   «под основным спрайтом»). Под ним они противоречили бы разделу «Порядок
   отрисовки» того же пункта (`zIndex` слоя + доля) и прежнему поведению
   `MapVolume`: плоский слой — основание блока, крыша рисуется последней.
3. **Контейнер статического слоя стал единичным**, а `data.scale` носят его
   дети (спрайт слоя и срезы), каждый вместе со своим сдвигом. Иначе срез
   пришлось бы двигать ОТНОСИТЕЛЬНО уже смещённого родителя — композиция
   двух параллаксов даёт `1 + k1 + k2 + k1*k2`, то есть не ту высоту, и
   формула перестала бы быть одной. `_hasFloorAt` и `update()` динамики
   переведены на сохранённый базовый масштаб.
4. **Ступень клина показывает часть прогона от `(i - 1) / K`, а висит на
   `i / K`** (план: «`progress >= i / K`»). При буквальном варианте верхняя
   ступень имела бы нулевую ширину. Видимая часть каждой ступени — ровно
   своя полоса, вместе они дают лестницу с нарастающей высотой.
5. **Клин НЕ тонируется `volume.sideTint`** (план 4.5 п. 4). При отсечке
   кадром видимая часть ступени — это сама наклонная поверхность горки, а
   не боковая грань: тонирование покрасило бы всю горку, кроме верхней
   полосы. Боковых граней у клина в этой схеме не видно вовсе.
6. **`SHADOW_SHEAR` (0.07) удалён, а не переехал в `parallax.shadowShear`**
   (план 4.7 допускал два числа). Корпус обязан смещаться ровно тем же
   числом, что и плита, на которой танк стоит, иначе он с неё съезжает —
   число может быть только одно.
7. **`Tracks` получил ещё и сервис `renderer`** (в плане назван только
   `levelView`): без рендерера не восстановить центр камеры.
8. **`applyParallax` ставит `position = -cam * k`**, а не
   `-camX * k * baseScale` из наброска 4.0: центр камеры приходит в мировых
   единицах, а не в единицах контейнера.
