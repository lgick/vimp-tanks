## 3.1 `collision_mask` обязан учитывать `climbing` (Д2, критично)

### Проблема

`core/src/level.rs:80-90`:

```rust
pub fn collision_mask(&self) -> Group {
    match self.transit {
        Transit::Falling { .. } => STATIC_LEVEL_GROUP,
        Transit::Ramp { low, high, .. } => (low..=high)
            .fold(Group::empty(), |acc, level| acc | level_group(level)),
        Transit::Grounded => level_group(self.level),
    }
}
```

Поле `climbing` не читается. Танк уровня 0, стоящий под клетками прогона
`1 → 2` (`terraces.rampStep`, `src/data/maps/terraces.js:34,137-139` — под
ним обычная проезжая земля), получает `Transit::Ramp { climbing: false,
low: 1, high: 2 }` и маску `GROUP_2 | GROUP_3`. Последствия:

- **проезжает сквозь стены уровня 0** (`static_level_interaction(0)` =
  `GROUP_1 | GROUP_9` — общих битов нет);
- перестаёт сталкиваться с наземными танками и ящиками;
- неуязвим для наземных выстрелов (`tanks.rs:976` фильтрует луч по
  `level_interaction(segment.level)`) и взрывов (`tanks.rs:1145-1180`);
- при этом простреливается с уровней 1—2.

Существующий тест `ramp_is_not_entered_from_under_the_bridge`
(`core/src/level.rs:525`) дефект не ловит: его фикстура — рампа `from: 0`,
поэтому бит земли и так в маске.

### Правка

```rust
Transit::Ramp { climbing, low, high } => {
    if climbing {
        // на прогоне тело видит геометрию всех уровней, которые прогон
        // соединяет: иначе на рампе 0 -> 2 танк провалился бы сквозь
        // промежуточную плиту или упёрся в невидимую стену
        (low..=high).fold(Group::empty(), |acc, level| acc | level_group(level))
    } else {
        // заехавшему сбоку прогон работает как плоская клетка ЕГО уровня —
        // и физика обязана видеть ровно этот уровень, иначе танк под
        // рампой 1 -> 2 проезжает сквозь наземные стены
        level_group(self.level)
    }
}
```

Плюс тело должно перестать видеть стражей прогона (этап 2.2) только при
`climbing == true` — там же, где собирается фильтр:

```rust
// страж рампы: борта и верхний торец. Поднимающийся проходит их насквозь
let ignore_guard = matches!(self.transit, Transit::Ramp { climbing: true, .. });
```

Найти всех, кто зовёт `collision_mask` (`core/src/tanks.rs` —
`sync_collision_groups`; `core/src/client/predicted_set.rs:191-193`;
`core/src/client/predictor.rs` — `resolve_world`), и провести флаг через
движковый `body_filter`.

### Тесты

`core/src/level.rs`, новая фикстура `overhead()` — карта, где прогон лежит в
гриде **уровня 1** (`from: 1, to: 2`), а под ним проезжая земля со стеной:

- `mask_under_a_high_ramp_stays_on_the_ground_level` — маска танка уровня 0
  на клетке прогона равна `level_group(0)`;
- `mask_on_a_ramp_covers_the_whole_run` — маска поднимающегося равна
  объединению уровней прогона;
- в `core/tests/sim.rs` — сценарий «танк уровня 0 упирается в стену,
  стоящую на клетке прогона 1 → 2» (краснеет на старом коде).

## 3.2 Гейт входа судит по своему прогону (Д11)

`core/src/level.rs:189-193`:

```rust
let climbing = match state.transit {
    Transit::Ramp { climbing, .. } => climbing,
    _ => entry_is_legal(state, &ramp, cell, levels),
};
```

Вердикт наследуется от **любой** предыдущей рампы: переезд из прогона A в
смежный прогон B сохраняет вердикт A, но применяет `low`/`high` от B. Это
бесплатный подъём (если A был законным) либо вечный запрет. Собственная
проверка «та же клетка того же прогона» внутри `entry_is_legal`
(`level.rs:288`) при этом недостижима.

Правка: хранить в `Transit::Ramp` номер прогона и сравнивать его.

```rust
Transit::Ramp { climbing, run, .. } if run == ramp.run => climbing,
_ => entry_is_legal(state, &ramp, cell, levels),
```

`Transit::Ramp` получает поле `run: u16`. Это часть сериализуемого состояния
(`#[derive(Serialize, Deserialize)]`) — проверить, что клиентская реплика и
дампы `sim` переживают добавление поля (у `Transit` тег `kind`, поле
добавляется аддитивно; тесты дампов поправить).

Тест: карта с двумя смежными прогонами, направленными в разные стороны;
въезд законный в первый и незаконный во второй — второй обязан отказать.

## 3.3 Уклон становится безразмерным, константы пересчитываются (Д7, физика)

После этапа 2 `RampSample::slope` приходит уже в безразмерном виде
(`rise * levelHeight / span`). Значит:

1. `core/src/motion.rs` править **не нужно** — формулы `drive_accel`
   (`:77-106`) корректны, у них был неверный масштаб входа.
2. `src/config/game.js:45-50` — пересчитать:

   ```js
   levels: {
     fallTime: 0.35,
     fallDamage: 15,
     maxFallDamage: ...,
     climbGravity: ...,          // подобрать
     climbMaxSpeedFactor: ...,   // подобрать
   },
   ```

   Порядок подбора:
   - `climbMaxSpeedFactor` — доля, на которую уклон 1.0 срезает потолок
     скорости. При `levelHeight = размер тайла` уклон на `terraces.rampSteep`
     (2 уровня на 4 клетки) = 0.5, на `rampLong` = 0.11, на
     `overpass.rampNorth` = 0.33. Цель: на крутом прогоне скорость заметно
     ниже, но подъём проходится на полном газе. Стартовое значение — 0.5.
   - `climbGravity` — мировых единиц/с² на единицу уклона. Ориентир:
     `accelerationFactor` модели (`src/data/models.js`) и требование
     «без газа танк скатывается с крутого прогона, но на полном газе
     поднимается». Стартовое значение — подобрать так, чтобы
     `grade * climbGravity` на `rampSteep` составляло 20—35 % тяги.
3. Тесты `core/src/motion.rs` (`:228-255`) переписать на **достижимые**
   значения уклона (0.1—0.5), а не на 0.5—1.0. Добавить тест «на `grade = 0`
   формула бит-в-бит прежняя» — он уже есть, сохранить.
4. Сценарии `tests/scenarios/bridge.json`, `terraces_climb.json`,
   `terraces_backside.json` обязаны остаться зелёными. Если крутой прогон
   перестал проезжаться — уменьшать `climbGravity`, а не менять карту.
5. `.max(0.25)` в `drive_accel` (`motion.rs:88`) при новом масштабе
   становится достижимым — проверить, что это осознанный нижний предел, и
   описать его комментарием.

## 3.4 Реплика бомбы кладёт её туда же, куда хост (Д12)

`core/src/client/shot.rs:370-376`:

```rust
let mut level = render.level;

if let Some(levels) = &self.levels
    && level >= 1
    && !levels.has_floor(level, render.x, render.y)
{
    level = 0;
}
```

Хост (`core/src/tanks.rs:1069-1090`) в той же ситуации зовёт
`levels.landing_level(level, x, y)` и дополнительно учитывает
`owner.level_state.input_locked()` (падающий роняет бомбу вниз). На
`terraces` бомба, брошенная с уровня 2 над разрывом перил, у хоста ложится
на плиту уровня 1, у клиента — на землю: локальный взрыв рисуется не на том
этаже и не совпадает с уроном.

Правка: вынести правило в **одну** функцию (например
`crate::level::bomb_level(levels, level, x, y, input_locked) -> u8`) и звать
её из обоих мест. Иначе третья копия появится при следующей задаче.

Тесты: юнит на `bomb_level` (три уровня, разрыв перил над плитой) и тест
клиентской реплики, что уровень совпал с хостовым на той же геометрии.

## 3.5 `level_state` входит в реконсиляцию (Д13)

`core/src/client/predictor.rs` реплеит движение от авторитетной позиции, но
`LevelState` (в частности `prev_cell` и `climbing`) продолжается с того
места, где закончился прошлый реплей. `prev_cell` при каждой реконсиляции
откатывается назад, и на клетке входа в прогон гейт может щёлкнуть
**только на клиенте** — класс расхождений, который заплатка этапа 7 прошлой
итерации (`!on_ramp` в `on_server_state`, `predictor.rs:527-575`) не
покрывает, а лишь маскирует.

Правка:

1. Включить `LevelState` в снапшот состояния, который предиктор сохраняет
   вместе с позицией и восстанавливает перед реплеем (найти структуру
   истории: поиск `history` / `snapshot` в `predictor.rs`).
2. После восстановления упростить условие `airborne` — оставить только то,
   что действительно нужно для синхронизации фазы падения по кадру
   (`fall_elapsed`), и записать в отклонениях, что именно упростилось.
3. Сторожевые тесты (существующие на реконсиляции падения и подъёма по
   рампе — сохранить) плюс новый: «реконсиляция на клетке входа в прогон не
   меняет вердикт гейта».

Порог дрейфа в сценариях (`throttle`, продольная скорость) — не ослаблять;
после правки он должен стать не хуже, чем сейчас (0.021 / 7).

## Отклонения и блокеры (заполнено при выполнении)

### Сделано сверх плана (вынужденная адаптация к движку 0.13/0.32)

1. **`role: 'z'` / `role: 'level'` в `src/config/snapshot.js`.** Движок
   0.13 узнаёт слоёную строку динамики карты по РОЛЯМ, а не по именам
   полей, и без них `load_map` падает с ошибкой. План этого шага не
   предусматривал.
2. **Клиентская реплика стражей прогона** (`Predictor::resolve_world`).
   Стражи этапа 2 — отдельные коллайдеры хоста, которых нет ни в одном
   гриде, поэтому предсказание проезжало там, где хост держит. Реплика
   собирает их теми же формулами (`RampRun` + `tile_size * 0.1`). Это
   вернуло в зелёное `terraces_backside.json`.
3. **`RenderState.falling`** — реплике выстрела нужен признак «танк
   падает», иначе общая с хостом `level::bomb_level` не может судить о
   заблокированном вводе.

### Отклонения от плана

1. **Sim-тест «бомба с уровня 2 над разрывом ложится на плиту 1» не
   добавлен.** На хосте эта ветка недостижима через ввод: падающий танк
   ввод не обрабатывает вовсе, а стоящий над разрывом танк уже падает.
   Правило покрыто юнит-тестом `bomb_falls_to_the_nearest_support_below`
   и клиентским `local_bomb_lands_where_the_host_lands_it`.
2. **Сценарий `terraces_under_ramp.json` не добавлен.** Заезд под прогон и
   упор в преграду уже покрывает `terraces_backside.json` (обе точки
   респауна team2 стоят ровно на этом), а правило маски — новый sim-тест
   `ground_wall_under_a_high_ramp_stops_the_tank`. Дублировать сценарий
   смысла нет; сценарии игровых правил не проверяют вовсе.
3. **`tank_cannot_enter_the_ramp_from_under_the_slab` переписан.** С
   этапа 2 «неправильный» торец прогона закрыт стражем, поэтому танк не
   проезжает прогон насквозь, а упирается в него — это и есть жалоба 3
   пользователя. Тест теперь требует упора.
4. **Условие `airborne` упрощено** не «по карте под авторитетной
   позицией» (`ramp_at`), а по откаченному состоянию
   (`LevelState::on_ramp()`): тот же вопрос, на который отвечает хост.

### Диагностика блокеров (выполнена)

Инструментация обеих сторон (`TanksSim::update_levels` и `Predictor::step`
печатали позицию, скорость, `angvel`, уровень, `transit` и контакты
Rapier) на прогоне `tests/scenarios/bridge.json`. Инструментация снята.

**Расхождение шаг в шаг.** До самого контакта обе стороны идентичны:
`x=72.61 y=395.07 v=(148.85, 0.87)`, уровень 1, `Grounded`. Следующий шаг:

| | результат шага | контакт |
| --- | --- | --- |
| хост | `x=72.93 y=394.80 v=(7.29, -40.45) w=5.521` | `Group(GROUP_2 \| GROUP_9)` в `(345.6, 403.2)`, полуразмеры `(268.8, 6.4)` |
| реплика | `x=72.81 y=395.08 v=(-7.65, -0.04) w=0.000` | нормаль `(1.0, 0.006)`, глубина `1.106` |

То есть **обе стороны бьются об одну и ту же стену — перила уровня 1 в
строке 31 `overpass`, — но видят её разной геометрией**:

- хост держит стены СКЛЕЕННЫМИ блоками (`GameMap::create_static` →
  `search_static_block`): здесь это одно тело шириной 537.6 (x 76.8…614.4);
- реплика собирает контакты ПОКЛЕТОЧНО
  (`client::collision::collect_tile_contacts`, тайл 12.8).

Танк въезжает в юго-западный угол этой стены по касательной: перекрытие по
x — 1.11, по y — 1.27. Rapier на длинном блоке разрешает контакт по оси Y
(отбрасывает танк вдоль стены на север, `w = 5.5`), реплика на отдельном
тайле берёт минимальную ось X и отбрасывает танк назад на запад без
вращения. Дальше траектории расходятся, и на кадре `serverTime 3500`
детектор ловит `angle`/`angvel`.

Проверено, что это НЕ:

- уровень/маска — обе стороны на уровне 1, `Grounded`, `prev_cell (5, 30)`;
- стражи прогона — контакт с группой `GROUP_2 | GROUP_9` (стена уровня 1 +
  статика), а не `GROUP_10`;
- вердикт гейта, откат `LevelState`, новые константы подъёма — расхождение
  сохраняется при откате каждого из них по отдельности.

Гэп поклеточной геометрии реплики существовал и раньше (база этапа 0 —
`angvel` до 0.98), но безразмерный уклон разогнал танк на выезде с рампы
до 148 ед/с, и касательный удар об угол стал жёстким.

### Решения по блокерам (приняты пользователем)

1. **`scripted_bot_drives_onto_the_bridge` (`core/tests/sim.rs`) — помечен
   `#[ignore]` до правки движка.** Нав-граф движка
   (`NavigationSystem::generate_layered`) считает клетки прогона обычной
   проезжей землёй уровня 0, а стражи их закрыли: бот упирается в верхний
   торец, уходит в `ClearingObstacle` и строит тот же путь заново.
   **Решение: правка вынесена в движковый долг — `stage_7.md` § 7.0.1**
   (релиз `vimp-engine-core 0.13.1` / `vimp-engine 0.32.1`); после
   публикации в танках поднимаются версии и снимается `#[ignore]`.
   Нав-граф движка (`NavigationSystem::generate_layered`) не знает о
   стражах прогона: бот уровня 0 упорно ломится в закрытый верхний торец
   рампы, не перестраивая путь, и на мост не попадает. Правка — движковая
   (нав-граф обязан считать клетки прогона непроезжими для тела уровня
   `low`, кроме законного входа с торца).
2. **`npm run sim:scenarios`: 4 из 12 сценариев красные** —
   `bridge.json`, `crosslevel.json`, `fall.json`, `terraces_climb.json`.
   Во всех — ОДНА реконсиляция из ~350, поля `angle`/`angvel`
   (Δ 0.21 / 2.81 при порогах 0.06 / 1.5), у подножия/вершины северной
   рампы `overpass`. База этапа 0: 11/11 зелёные, максимум по `angvel`
   0.98. Проверено:
   - откат `climbGravity`/`climbMaxSpeedFactor` к прежним значениям —
     не помогает;
   - откат правки маски (Д2) — не помогает;
   - откат отката `LevelState` в реконсиляции — не помогает;
   - зеркало стражей в реплике — помогает `terraces_backside`, но не этим
     четырём.
   Причина найдена (см. «Диагностика блокеров»): реплика собирает стены
   поклеточно, хост — склеенными блоками, и на касательном ударе об угол
   стены решатели выбирают разные оси. Правка — движковая
   (`client::collision::collect_tile_contacts` обязана видеть те же
   склеенные блоки, что `GameMap::create_static`).
