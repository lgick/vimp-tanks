## Этап 1. Сделать тесты прыжка не-холостыми ✅ выполнен

**Файл**: `core/tests/sim.rs`

### 1.1 `a_jump_never_leaves_the_map`

Сейчас тест только гоняет танк 900 шагов и проверяет периметр + `peak < 1.45`.
При выключенном прыжке танк доезжает до дальних перил и стоит — тест зелёный.

Нужно добавить **доказательство факта полёта**. Признак полёта, доступный
снаружи ядра: высота `tank_z` не равна целому уровню `level_of`, ПРИ ЭТОМ танк
не на рампе. Простой и достаточный признак для этого прогона: после того как
танк поднялся на уровень 1 (`level_of == 1`), его `z` хотя бы раз строго
больше 1 — на плите он лежит ровно на 1.0, а на рампу с уровня 1 он уже не
возвращается.

Внутри существующего цикла `for _ in 0..900` завести флаг:

```rust
let mut climbed = false;
let mut jumped = false;
```

и в теле цикла, после `core.step(DT)` и вычисления `(x, y)`:

```rust
let z = tank_z(&core, 1);

if level_of(&core, 1) == 1 {
    climbed = true;
}

// на плите танк лежит ровно на 1.0; всё, что выше, — дуга прыжка
if climbed && z > 1.0 + 1e-3 {
    jumped = true;
}

peak = peak.max(z);
```

После цикла, ДО существующего `assert!(peak < 1.0 + 0.45, ...)`:

```rust
assert!(climbed, "танк обязан подняться на плиту моста");
assert!(
    jumped,
    "сход с рампы обязан оторвать танк от плиты — иначе тест сторожит пустоту"
);
```

И заодно ужесточить нижнюю границу дуги — она обязана быть заметной:

```rust
assert!(
    peak > 1.0 + 0.05,
    "дуга обязана быть различимой, peak = {peak}"
);
```

Замер даёт `peak = 1.16`, так что запас до 1.05 достаточный, а до
`1.45` (потолок `jumpClearance`) остаётся прежним.

### 1.2 `a_jump_lands_on_the_bridge`

## Этап 2. Инварианты прыжка — в `TanksConfig::validate()` ✅ выполнен

**Файл**: `core/src/config.rs`

### 2.1 Почему это нужно

Центральное решение задачи (`plan/done/tank-dynamics-review/README.md`,
таблица «Решения, принятые до начала работ»): перелёт стен остаётся
механикой ядра, но становится недостижимым штатным прыжком, потому что
`jumpClearance` поднят выше максимальной дуги.

Сейчас этот инвариант проверяет **только** `tests/config/game.test.js` —
JS-тест над `src/config/game.js` ЭТОГО репозитория. `LevelRules` при этом
читается ядром из произвольного конфига (`coreParams.levels`), и у него есть
дефолты для всех трёх участвующих полей. Любая карта или игра, которая
переопределит блок `levels`, молча вернёт проблему 3.

Инвариант ломается не только явным задиранием `maxLaunchVz`. Пример, который
JS-тест не увидит в принципе: `fallTime: 0.5` при остальных дефолтах даёт
`g = 2/0.25 = 8`, дуга `3.5²/16 = 0.77` — **выше** `jumpClearance 0.45`,
и штатный прыжок снова снимает маску коллизий вместе с периметром карты.

### 2.2 Правка

В `TanksConfig::validate()`, в блок проверок `levels`, после существующих
проверок `max_launch_vz` и `jump_clearance` добавить:

```rust
// инвариант задачи «динамика танка»: перелёт стен остаётся механикой
// ядра, но штатным прыжком недостижим. Ломается не только задранным
// maxLaunchVz — достаточно поднять fallTime (гравитация падает, дуга
// растёт). Карте, которой перелёт НУЖЕН, достаточно поднять
// jumpClearance заодно с maxLaunchVz — проверка этого не запрещает,
// она требует, чтобы намерение было записано в конфиг явно
if self.levels.max_launch_vz > 0.0 && self.levels.jump_clearance > 0.0 {
    let g = 2.0 / (self.levels.fall_time * self.levels.fall_time);
    let peak = (self.levels.max_launch_vz * self.levels.max_launch_vz) / (2.0 * g);

    if peak >= self.levels.jump_clearance {
        return Err(format!(
            "levels: jump arc maxLaunchVz²/(2g) = {peak} must be < jumpClearance ({}); \
             g = 2/fallTime² = {g}",
            self.levels.jump_clearance
        ));
    }
}
```

Условие `max_launch_vz > 0.0` обязательно: `0` означает «потолка нет»,
дуга тогда не ограничена и формула бессмысленна. Условие
`jump_clearance > 0.0` тоже: `0` документирован как «стены пропадают в момент
отрыва», то есть карта явно хочет перелёт.

`fall_time` уже проверяется выше по файлу на `> 0` (убедиться перед правкой,
иначе деление даст `inf`/`NaN`; если проверки нет — добавить её первой).

### 2.3 `maxLaunchVz` против `minLaunchVz` (проблема 3)

В `core/src/level.rs` потолок применяется к `raw_vz` **до** сравнения с
порогом `min_launch_vz`:

```rust
let vz = if rules.max_launch_vz > 0.0 { raw_vz.min(rules.max_launch_vz) } else { raw_vz };

if vz >= rules.min_launch_vz { /* взлёт */ }
```

Значит при `maxLaunchVz < minLaunchVz` прыжок не начнётся **никогда**, при
любом уклоне и любой скорости, и конфиг при этом формально валиден. Добавить
в `validate()` рядом с 2.2:

```rust
// потолок применяется ДО порога (core/src/level.rs), поэтому потолок
// ниже порога — это не «низкий прыжок», а выключенный прыжок, причём
// молча. Выключается прыжок нулевым rampLaunchFactor
if self.levels.max_launch_vz > 0.0 && self.levels.max_launch_vz < self.levels.min_launch_vz {
    return Err(format!(
        "levels.maxLaunchVz ({}) must be >= minLaunchVz ({}) — a lower ceiling \
         disables jumping entirely; use rampLaunchFactor = 0 for that",
        self.levels.max_launch_vz, self.levels.min_launch_vz
    ));
}
```

## Этап 3. Признак полёта не должен зависеть от округления ✅ выполнен

**Файлы**: `src/client/parts/Tank.js`

### 3.1 Диагноз

`core/src/tank.rs::snapshot_row` кладёт в кадр `vz: round2(...)` — вертикальная
скорость округляется до сотых. Клиент использует `vz !== 0` в двух ролях:

1. `_updateShadow` — «рисовать ли тень вообще»;
2. `_groundZ()` — «где опора: `_physLevel` (в полёте) или `_z` (на земле)».

На вершине дуги `vz` проходит через ноль, и `round2` даёт **ровно 0.00** в
окне |vz| < 0.005. При `g = 16.33` уровней/с² это окно длится ≈ 0.6 мс — редко,
но детерминированно: когда кадр в него попадает, тень на один кадр гаснет,
а `_groundZ()` скачком уезжает с опоры на `_z`. Логически же признак неверен
сам по себе: `vz === 0` означает «скорость округлилась в ноль», а не «танк
на опоре».

Кадр везёт достаточно, чтобы признак был точным: `z` (`f32`, `lerp`) и `level`
(`u8`, discrete). В полёте и в падении `level` держит уровень ОТРЫВА всю дугу
(`core/src/level.rs`, `step_airborne` не трогает `state.level` до посадки), а
на плите `z == level`. На рампе `z` дробное и не равно `level` — но на рампе
`vz` в кадре ровно 0 всегда (`snapshot_row` берёт `vz` только из
`Transit::Airborne`), так что рампу по-прежнему отличает именно `vz`.

### 3.2 Правка: чинить источник, а не признак

Соблазн — расширить признак на клиенте (`vz !== 0 || _z !== _physLevel`).
Так делать **нельзя**: на рампе `z` тоже расходится с `level` при нулевой
`vz`, и тень вернётся на подъём — ровно туда, откуда её убирали. Признака
рампы в кадре нет.

Значит чинить надо источник. `core/src/tank.rs::snapshot_row` округляет `vz`
до сотых наравне с координатами, хотя это поле работает ФЛАГОМ. Ненулевая
скорость обязана оставаться ненулевой:

```rust
            // `vz` в кадре работает флагом полёта (src/client/parts/Tank.js,
            // src/client/landing.js), поэтому округляется не как координата:
            // round2 на вершине дуги превращал реальную скорость в ровный
            // ноль, и тень на кадр считала летящий танк стоящим
            vz: match self.level_state.transit {
                Transit::Airborne { vz, .. } => {
                    let rounded = round2(vz);

                    // знак сохраняем: детектор касания смотрит именно на него
                    if rounded == 0.0 && vz != 0.0 {
                        vz.signum() * 0.01
                    } else {
                        rounded
                    }
                }
                _ => 0.0,
            },
```

Инварианты не затронуты: ширина поля и порядок в строке те же, реплика берёт
`vz` из сырого кадра тем же полем, паритет предиктора считает шаг по
собственному состоянию, а не по округлению кадра.

Клиент при этом не правится вовсе: после этой правки `vz === 0` в кадре
означает ровно «танк на опоре», и `_groundZ()`/`_updateShadow` становятся
корректными без единой строки изменений. В `_groundZ()` дописать одну строку
комментария о том, ПОЧЕМУ нулю можно верить:

```js
  // `vz` в кадре — точный флаг: ядро специально не даёт ненулевой скорости
  // округлиться в ноль (`snapshot_row`, core/src/tank.rs)
```

### 4.1 Диагноз

Проблема 1 исходного ревью («танку не хватает объёма, картинка плоская»)
после отката экструзии закрывается ТОЛЬКО светотенью `tilt.shading`. Но
половина эффекта не видна:

- `Tank._updateView` берёт базу `baseTint = levelView.tintFor(this._level)`;
- `seeThroughTint` (`src/client/seeThrough.js:65`) возвращает `cfg.lowerTint`
  только для уровней НИЖЕ уровня игрока, а для своего и верхних — `0xffffff`;
- `scaleTint` зажимает каналы в `0xff`.

Значит для своего танка и для всех танков на своём/верхнем ярусе множитель
`shade > 1` не даёт ничего: каналы уже на потолке. Работает только затемнение.
Это зафиксировано комментарием в тесте
(`tests/client/parts/Tank.test.js`, «наклон затемняет корпус, ровная земля —
нет»), но **не** в конфиге и не в документации, где `shading` описан как
симметричный размах яркости («how far the hull's brightness swings»).

### 4.2 Правка: сделать светотень честно односторонней

Симметричный эффект в 8-битном тинте поверх белого невозможен без предварительного
затемнения базы. Предварительно затемнять корпус нельзя — это изменит вид
ровно стоящего танка на всех картах, включая плоские. Поэтому эффект делается
явно односторонним: наклон ТОЛЬКО затемняет, глубина зависит от того,
насколько нормаль ушла от света.

В `src/client/tilt.js` заменить хвост `tiltShade`:

```js
  const len = Math.hypot(lightDir[0], lightDir[1]) || 1;
  const dot = (nx * lightDir[0] + ny * lightDir[1]) / len;

  // множитель ТОЛЬКО затемняет. Симметричного размаха в 8-битном тинте
  // поверх белого не получить: тинт уровня для своего и верхних ярусов —
  // 0xffffff (`seeThroughTint`), и подсветка упирается в потолок канала,
  // то есть пропадает ровно у того танка, ради которого эффект и заведён.
  // Поэтому светотень считает УХОД нормали от света: 1 — грань смотрит на
  // свет, 1 − shading — полностью отвёрнута
  return 1 - (1 - dot) * 0.5 * shading;
```

При `dot = 1` (грань к свету) множитель 1 — корпус не темнеет; при `dot = -1`
(отвёрнут) — `1 - shading`; при `dot = 0` (ровный танк) — `1 - shading/2`.

**Последствие**: ровно стоящий танк станет темнее на `shading/2`. Это меняет
вид на плоских картах, поэтому формулу надо нормировать так, чтобы ровный
танк оставался нетронутым. Правильный вариант — считать уход от света ОТ
РОВНОГО положения, а не от направления света:

```js
  // dot ∈ [−1, 1] — проекция наклона нормали на свет. Ровный корпус даёт
  // dot = 0 и множитель ровно 1: плоская карта обязана выглядеть как
  // раньше. Наклон ОТ света затемняет; наклон НАВСТРЕЧУ свету не
  // подсвечивает, а только снимает затемнение — подсветки поверх белого
  // тинта в 8 битах всё равно нет
  return 1 - Math.max(0, -dot) * shading;
```

Итог: `dot ≤ 0` (отвёрнут) → `1 − |dot|·shading`; `dot > 0` (к свету) → 1.
Ровный танк — 1. Плоские карты не затронуты.

Соответственно `clamp(..., 0.5, 1.5)` в `Tank._updateView` заменить на
`clamp(..., 0.0, 1.0)` и вынести границы в именованные константы файла:

```js
// светотень только затемняет (см. tiltShade): множитель зажат в [0, 1]
const SHADE_MIN = 0;
const SHADE_MAX = 1;
```

  сборки; это отдельная задача про тестовую инфраструктуру, а не про динамику
  танка. После этапа 2 расхождение по `jumpClearance` хотя бы перестанет быть
  молчаливым: `validate()` уронит конфиг.
- **Не оживляем мёртвые в поставке ветки ядра.** При дуге ≤ 0.375 уровня
  недостижимы обе: `clear_walls` (порог 0.45) и ветка `jumped` в
  `step_airborne` (посадка на ярус ВЫШЕ требует дуги ≥ 1 уровня). Первое —
  осознанное решение исходной задачи. Второе в плане не обсуждалось и теперь
  тоже недостижимо ни одним штатным прогоном, оставаясь под юнит-тестами со
  своими `rules`. Удалять её нельзя (это механика для карт с собственной
  настройкой), а оживлять — значит менять решение по перелёту стен. Оставляем
  как есть, но фиксируем здесь, чтобы следующая правка динамики знала: ветка
  боевыми прогонами не покрыта.
- **Не трогаем `vimp-engine`.** Все правки умещаются в этот репозиторий.
