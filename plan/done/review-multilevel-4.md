## Этап 1. Стражи прогона: реплика обязана повторять хоста (К1) ✅ выполнен

**Приоритет: критический.** Это прямое расхождение предсказания с
авторитетной симуляцией, и документация закрепляет его как правильное.

### Что не так

`T core/src/client/predictor.rs:1061`:

```rust
body.on_ramp =
    map.is_some_and(|levels| levels.ramp_at(body.body.x, body.body.y).is_some());
```

и ниже (`:1167`) любое тело с `on_ramp == true` пропускается сквозь
стражей. Комментарий рядом утверждает: «так же пропускает тело хост
(`map::body_filter`)». Это неверно для ОБОИХ видов предсказанных тел:

1. **Ящики карты.** Хост ставит им маску в
   `E packages/engine/core/src/map.rs:1694` —
   `collider.set_collision_groups(levels_interaction(after))`. Вариант
   `levels_interaction_on_ramp` для тел карты не зовётся НИГДЕ. То есть
   ящик, столкнутый на прогон, у хоста упирается в борт, а у реплики
   проходит насквозь.
2. **Чужие танки.** Хост судит по гейту:
   `T core/src/tank.rs:572` — `if self.level_state.on_ramp()`, а
   `LevelState::on_ramp()` — это `Transit::Ramp { climbing: true, .. }`.
   Танк, заехавший на прогон сбоку (`climbing == false`), у хоста стражей
   ВИДИТ. Реплика его пропускает.

Свой танк посчитан правильно (`tank_on_ramp = self.level_state.on_ramp()`),
поэтому сценарии и зелёные: в `tests/scenarios/*.json` чужой танк на
прогоне и ящик на прогоне одновременно со стражем не встречаются.

Симптом в бою: чужой танк, заехавший на горку боком, у зрителя едет
вверх, а на хосте стоит у борта — рывок на каждом кадре; ящик,
столкнутый на середину прогона, у зрителя проезжает сквозь борт.

### Решение

Правило «вижу ли я стражей» обязано быть ОДНИМ и приходить из того же
источника, что у хоста, — а не вычисляться реплики ради.

**1.1. Ящики карты — точный паритет.**
`MapDynamics` заполняет `PredictedBody.on_ramp = false` всегда (хост для
тел карты `levels_interaction_on_ramp` не зовёт вовсе). Если в будущем
хост начнёт пускать ящики по прогонам, правило меняется в двух местах
СРАЗУ, и это фиксируется докстрокой на `body_filter`.

**1.2. Чужие танки — вывести `climbing` из того, что уже едет в кадре.**
Добавлять поле в снапшот не нужно. `level::step_layered` для тела на
прогоне, которое НЕ поднимается, делает ровно это:

```rust
if !climbing {
    state.slope_vec = [0.0, 0.0];
    state.z = state.level as f32;   // <-- z ровно равен уровню
    return LevelEvent::None;
}
```

а для поднимающегося `z = lerp(from, to, progress)`. Значит для тела на
клетке прогона признак точен и бесплатен:

```rust
// тело на прогоне поднимается законно тогда и только тогда, когда его
// высота отличается от целого уровня: хост, отказав гейту, кладёт
// z = level ровно (`level::step_layered`)
on_ramp = ramp_at(x, y).is_some() && (z - level as f32).abs() > 1e-3
```

Граничный случай «законно поднимающийся стоит ровно на торце (z == level)»
безопасен: у подножия бортов с `vimp-engine-core 0.17.0` нет, а у вершины
уровень тела уже `high`, и маска стража (`ramp_guard_interaction(low)`)
его не ловит.

Для этого `RemoteTanks` обязан класть `z` строки в само тело: значение
уже читается (`core/src/client/remote_tanks.rs:324` — `meta.z`), но в
`PredictedBody.z` не попадает (пишется только `body.level`, строки 312 и
363). Добавить `body.z = field_f32(&row.fields, FIELD_Z);` в обе точки.

**1.3. Одна функция на все стороны.** Вынести признак в `crate::level`:

```rust
/// Видит ли тело стражей прогона. Правило одно на хост и на реплику:
/// у танка — вердикт гейта (`LevelState::on_ramp`), у тела карты —
/// «никогда», а реплика чужого танка выводит вердикт из высоты строки.
pub fn body_on_ramp(levels: &MapLevels, x: f32, y: f32, z: f32, level: u8) -> bool
```

и звать её из `resolve_world`. Комментарий у вызова переписать: сегодня он
описывает поведение, которого у хоста нет.

**1.4. Альтернатива, если 1.2 покажется хрупкой** — передать `climbing`
битом в строке танка (`TANK_FIELD_*`, `src/config/snapshot.js`,
`TankRow` в `core/src/tanks.rs`). Это правка контракта снапшота: +1 поле,
`vimp-contract --strict`, обновление `docs/*/configuration.md`. Дороже, но
не зависит от инварианта `z == level`. **Рекомендуется 1.2**, 1.4 — на
случай, если паритет-тест 1.5 покажет расхождение.

**1.5. Тесты** (`core/src/client/predictor.rs`, `mod tests`):

- ящик на КЛЕТКЕ прогона борт держит — переписать существующий
  `a_predicted_body_on_the_run_passes_the_guard` на обратное утверждение
  (сегодня он закрепляет дефект);
- чужой танк с `z == level` на клетке прогона борт держит;
- чужой танк с дробным `z` борт пропускает;
- свой танк — поведение прежнее (оба существующих теста без изменений).

**1.6. Документация.** `docs/en/core.md:582-585` и зеркальное место в
`docs/ru/core.md` сегодня пишут: «the replica lets through ANY body
standing on a run cell … exactly as the host reads it». Переписать на
реальное правило. `CHANGELOG.md` → `### Fixed`.

- `grep -n "ramp_at" core/src/client/predictor.rs` — ни одного места, где

## Этап 2. Возврат уровня наверх (К2) ✅ выполнен

**Приоритет: высокий.**

### Что не так

После `ramp-entry-descent` кадр правит уровень реплики только ВНИЗ
(`predictor.rs:655`), а `correct_level` не правит ничего. Наверх уровень
возвращают ровно два пути:

1. `adopt_level` — один раз, на первом кадре со своим `gameId`
   (`client/mod.rs:333`, условие `known_id != Some(my_id)`);
2. `rewind_level_state` с ПУСТОЙ историей — то есть после `reset()`,
   смены карты или разрыва длиннее `HISTORY_MAX_AGE`.

Если реплика оказалась НИЖЕ хоста, а история уровня кадр покрывает,
расхождение вечное — с тем же набором симптомов, что чинил сам план
(чужая маска коллизий, чужой слой, чужой тинт, чужой масштаб корпуса).
Попасть туда можно как минимум так:

- вердикт гейта разошёлся (реплика отказала входу, хост пустил, или
  наоборот) — а гейт как раз сложный и зависит от `prev_cell`;
- респаун на плите БЕЗ `camera.forceReset` (сегодня `reset()` зовётся
  только по нему, `client/mod.rs:297`) — `adopt_level` второй раз не
  сработает, `known_id` уже равен `my_id`;
- телепорт/снап уровня на хосте (`Tank::set_level`) вне респауна.

Обратная асимметрия обоснована («запоздавший кадр врёт только вверх»), но
из неё не следует, что подъём принимать НЕЛЬЗЯ, — следует только, что его
нельзя принимать МГНОВЕННО.

### Решение

Ввести «стойкое несогласие»: подъём принимается, когда кадр держит уровень
выше реплики дольше, чем может врать запоздавший кадр.

- В `Predictor` добавить `level_disagreement: u8` (или `f64` — время
  первого несогласия).
- В `begin_reconcile`, в ветку «кадр выше реплики, не на прогоне,
  не `airborne`»: если несогласие держится подряд `LEVEL_ADOPT_FRAMES`
  кадров — применить кадр (тем же кодом, что `adopt_level`) и обнулить
  счётчик. Любое согласие обнуляет счётчик немедленно.
- Константу вывести из физики запаздывания, а не подобрать: кадры
  запаздывают на буфер интерполяции (десятки миллисекунд), а не на
  секунды; `LEVEL_ADOPT_FRAMES = 8` при ~20 кадрах/с — это ~0.4 с, заведомо
  больше буфера и заведомо незаметно как «мигание». Число вынести
  в `LevelRules` (`src/config/game.js`), чтобы его правил конфиг, а не
  перекомпиляция.

Отдельно: сделать `adopt_level` идемпотентным по смыслу «уровень из кадра
при отсутствии предсказания» и звать его ещё и при смене `condition`
`0 → 3` (респаун), а не только при смене `gameId`.

### Тесты

- кадр выше реплики один-два раза подряд — уровень НЕ меняется (старый
  баг со спуском не возвращается);
- кадр выше реплики `LEVEL_ADOPT_FRAMES` раз подряд — уровень принят;
- чередование «выше / согласие / выше» — уровень НЕ меняется;
- на прогоне рампы подъём не принимается никогда (как и понижение).

### Документация

`docs/en|ru/core.md`, раздел про реплику уровня: описать обе стороны
правила и назвать константу. `CHANGELOG.md` → `### Fixed`.

## Этап 3. Диагональ между полосами широкой горки (К3) и порог заезда сбоку (К14) ✅ выполнен

**Приоритет: средний.**

### К3. Что не так

`T core/src/level.rs::is_lane_change`:

```rust
along == 0 && across.abs() == 1 && a.block == b.block
```

Перестроение между полосами засчитывается, только если индекс клетки
ВДОЛЬ оси не изменился. Шаг по диагонали (изменились обе координаты
клетки) под правило не попадает, вердикт гейта наследован не будет, и
`entry_is_legal` отработает как новый вход — по клетке СЕРЕДИНЫ прогона,
то есть откажет. Подъём обрывается прямо посреди горки: `climbing`
становится `false`, `z` снапится к уровню, маска коллизий схлопывается до
одного уровня.

На широкой горке диагональное движение — норма, а не экзотика. Событие
редкое (нужно, чтобы за один шаг сменились обе клетки), поэтому в
сценариях не поймалось, — но это ровно тот тихий дефект, который потом
ловят глазами и списывают на «дёрнулось».

### Решение

Признак «та же горка» уже есть и он точный — `block`. Шаг вдоль оси для
перестроения между полосами ничего не решает:

```rust
// перестроение между полосами ОДНОЙ горки: признак — номер блока, а не
// направление шага. Диагональный шаг меняет обе клетки сразу, и
// требование `along == 0` обрывало подъём на середине широкой горки
fn is_lane_change(levels: &MapLevels, prev: (i32, i32), ramp: &RampSample) -> bool {
    let Some(prev_run) = run_at_cell(levels, prev) else {
        return false;
    };
    let runs = levels.runs();
    let (Some(a), Some(b)) = (runs.get(prev_run as usize), runs.get(ramp.run as usize)) else {
        return false;
    };

    a.block == b.block && prev_run != ramp.run
}
```

Параметр `cell` становится не нужен — убрать из сигнатуры. Ограничение
`across.abs() == 1` тоже лишнее: у полос одного блока соседство поперёк
оси гарантировано построением (`MapLevels::build_runs` режет сплошной
прямоугольник тайлов), а «прыжок через полосу» за один шаг физически
невозможен.

Осторожно: правило уже НЕ должно ловить вход С ТОРЦА в соседнюю полосу —
но там `prev_run` равен `None` (прошлая клетка не рампа) либо принадлежит
другому блоку, и функция и так вернёт `false`.

**Тесты:** подъём по широкой горке диагональю через границу полос не
теряет `climbing`; вход с торца в полосу широкой горки по-прежнему судит
гейт; ступенчатый блок (полосы разной длины, разные `block`) остаётся
разными горками.

### К14. Порог заезда сбоку

`MAX_SIDE_ENTRY_RISE = 0.5` сравнивается строгим `>`, поэтому скачок
высоты ровно на пол-уровня ЗАКОНЕН. На прогоне длиной в одну клетку
(бортов у него нет вовсе) это даёт мгновенный скачок `z` на 0.5 при
заезде сбоку — видимый «щелчок» корпуса и тени.

Решение — не менять число вслепую, а:

1. заменить `>` на `>=` (скачок строго меньше половины уровня);
2. вынести константу в `LevelRules` (`src/config/game.js`), рядом с
   `fall_time`: это игровое правило, а не физическая постоянная;
3. описать его в `docs/en|ru/gameplay.md` (сегодня правило входа на горку
   там описано без этого ограничения) и в `docs/en|ru/core.md`.

## Этап 4. Рендер: падающий ящик и юбка клина (К4, К5) ✅ выполнен

**Приоритет: средний.**

### К4. Падающий ящик рисуется уровнем, а не высотой

`ramp-entry-descent` починил это для танка (`Tank.js`):

```js
const level = Math.min(data[M1_LEVEL] || 0, Math.round(this._z));
```

но тела карты падают по тем же правилам (`map::step_body_level`), а
`MapObject.js` про высоту не знает вовсе:

- `update()` читает только `data[C_LEVEL]` (`:132`), хотя `C_Z` в строке
  есть (`src/client/snapshotFields.js:57`);
- `render()` сдвигает параллакс на `this._level * shear` (`:110`), то есть
  падающий ящик не опускается визуально ВООБЩЕ и «телепортируется» на
  нижний слой в момент касания;
- `alphaFor(level, x, y)` зовётся без `z` (`:98`), поэтому прозрачность
  падающего ящика считается по высоте плиты, с которой он сорвался.

**Решение** — повторить правило танка дословно:

```js
this._z = data[C_Z] || 0;

// уровень ОТРИСОВКИ, а не физический: пока тело падает, хост держит
// `level` тем уровнем, с которого оно сорвалось (`map::step_body_level`)
const level = Math.min(data[C_LEVEL] || 0, Math.round(this._z));
```

- `render()`: параллакс — `this._z * parallaxConfig.shear`, а не
  `this._level * shear`; условие раннего выхода `if (!this._level)` меняется
  на `if (!this._level && !this._z)`;
- `alphaFor(this._level, this._worldX, this._worldY, this._z)`.

Правило `min(level, round(z))` повторяется теперь в двух партах — вынести
его в `src/client/levelZ.js` (или в новый `src/client/renderLevel.js`)
одной функцией `renderLevel(level, z)` и звать из обоих.

**Тесты** (`tests/client/parts/map/MapObject.test.js`): строка с
`z = 0.4, level = 1` даёт `zIndex` уровня 0; параллакс падающего тела
меняется между кадрами; `alphaFor` получает `z` строки.

### К5. Юбка клина рисует борта, которых в физике больше нет

`E map::ramp_guards` после `ramp-entry-descent`:

```rust
// клетка подножия остаётся открытой со всех сторон
let (rail_min, rail_max) = if run.sign > 0 { (run.min + tile, run.max) }
                           else            { (run.min, run.max - tile) };
...
// прогон в одну клетку — это одно подножие: бортов у него нет
if rail_max - rail_min > tile / 2.0 { ... }
```

А `T src/client/parts/map/extrusion.js::buildRampSkirt` по-прежнему строит
борта во ВСЮ длину прогона (`points` вершин от `col0/row0` до `col1/row1`)
и строит их даже у прогона длиной в одну клетку. Собственный комментарий
модуля при этом обещает обратное:

> Строятся ровно те грани, что закрыты физически: два борта ВДОЛЬ оси … и
> торец на ВЕРХНЕМ конце.

Картинка показывает стену там, где физика пускает, — то есть ровно тот
разрыв «видно и нельзя проехать / не видно и можно», ради закрытия
которого прогоны в рендер и потянули из ядра.

**Решение.** Строить юбку по той же геометрии, что стражей:

1. лучший вариант — вынести из `E map::ramp_guards` чистую функцию
   «границы бортов прогона» (`ramp_rail_span(run, tile) -> Option<(f32, f32)>`)
   и отдать её клиенту в `RampRunView` двумя полями (`railMin`, `railMax`,
   `null` — бортов нет). Тогда формула остаётся одна на три потребителя
   (коллайдеры хоста, стражи реплики, юбка рендера);
2. дешёвый вариант без правки движка — повторить отсечку на JS в
   `buildRampSkirt`: борта начинаются с вершины `i = 1` при `sign > 0`
   (с `points - 2` при `sign < 0`), а при `cells <= 1` борта не строятся
   вовсе. Но это ВТОРАЯ копия формулы — ровно то, что решение 1 плана
   `review-multilevel-3` запретило. **Рекомендуется вариант 1.**

Торцевую грань трогать не нужно: она и у стражей одна, на «неправильном»
конце.

**Тесты** (`tests/client/parts/map/extrusion.test.js`): у прогона длиной
в одну клетку юбка состоит только из торца; у длинного прогона нижняя
кромка бортов начинается со второй клетки; число вершин и квадов
пересчитано (`columns`, `quads` — константы в `buildRampSkirt`).

## Этап 5. Жизненный цикл состояния уровня (К6, К8) ✅ выполнен

**Приоритет: средний.**

### К6. `set_map` не чистит состояние уровня

`Predictor::set_map` (`core/src/client/predictor.rs:377`) обновляет
`guards` и `levels`, но НЕ трогает `level_state` и `level_history`. После
смены карты:

- `level_state.prev_cell` — клетка ПРЕДЫДУЩЕЙ карты, и `entry_is_legal`
  судит по ней первый вход на прогон новой;
- `level_history` хранит снимки, снятые на старой геометрии, и
  `rewind_level_state` их восстановит — как раз обойдя ту ветку «истории
  нет, берём из кадра», которую задача и добавила.

Сегодня спасает только то, что смена карты обычно приходит с
`camera.forceReset` → `reset()`. Полагаться на это молча — то же, что
полагалось на порядок кадров до задачи.

**Решение:** в конце `set_map` —

```rust
// геометрия сменилась: клетка входа, вердикт гейта и вся история уровня
// относятся к СТАРОЙ карте. Оставить их — значит судить вход на прогон
// новой карты по клетке прежней (см. `entry_is_legal`)
self.level_state = LevelState::default();
self.level_history.clear();
self.authoritative_level = None;
```

**Тест:** после `set_map` на другую карту `level_state` дефолтный, а
`rewind_level_state` уходит в ветку «истории нет».

### К8. `authoritative_level` не сбрасывается

`client/mod.rs:270` зовёт `correct_level` ТОЛЬКО когда своя строка в кадре
нашлась. Если её нет (танк уничтожен, частичный CLEAR, `null`-маркер),
`authoritative_level` держит значение прошлого кадра — и ветки `airborne`
и «понижение» в `begin_reconcile` продолжают действовать по протухшим
данным, включая ветку «истории нет» в `rewind_level_state`.

**Решение:** сделать `correct_level` принимающим `Option<(f32, u8)>` (или
добавить `clear_authoritative_level()`) и звать его на КАЖДОМ
`begin_reconcile` — с `None`, когда строки нет.

**Тест:** кадр без своей строки после кадра с уровнем 1 не оставляет
`authoritative_level`.

## Этап 6. Центр камеры как сервис (К7) ✅ выполнен

**Приоритет: средний.**

### Что не так

Этап 4 плана `review-multilevel-3` свёл дыру в плите и alpha сущностей в
одну проекцию — но источником центра камеры сделал ОДИН парт:

- `src/client/parts/Tank.js:348` — `if (this._levelView && this._isLocal())
  { this._levelView.setCamera(camera); }`;
- `src/client/levelView.js:36` — `setCamera` просто кладёт значение в
  состояние, `alphaFor` читает его как есть.

Следствия:

1. **Нет локального танка — нет камеры.** Наблюдатель, момент между
   смертью и респауном, кадры до появления `localPlayer.id`: `state.camera`
   остаётся `null` или протухшим. При этом `MapLayer.render()` считает
   камеру САМ (`cameraCenter(this._container.parent, this._renderer)`), и
   дыра едет по свежей проекции, а alpha сущностей — по старой. Это и есть
   Д8, вернувшийся с другой стороны.
2. **Порядок партов в кадре не определён.** Парт, чей `onRender` вызван
   раньше локального танка, использует камеру ПРОШЛОГО кадра. На движении
   это отставание в один кадр у части сущностей и ноль у остальных.

### Решение

Камера — свойство кадра, а не парта. Сервис обязан добывать её сам и один
раз за кадр:

```js
// src/client/levelView.js
export function createLevelView(cfg = seeThrough, deps = {}) {
  const state = { level: 0, x: 0, y: 0, z: 0, camera: null, frame: -1 };

  // центр камеры — свойство КАДРА, а не парта: считается лениво, один раз
  // на тик общего тикера, и одинаков для дыры в плите и для alpha сущностей
  const camera = () => {
    const tick = Ticker.shared.lastTime;

    if (state.frame !== tick) {
      state.frame = tick;
      state.camera = cameraCenter(deps.stage?.(), deps.renderer);
    }

    return state.camera;
  };
  ...
}
```

`stage` и `renderer` сервис получает в `hooks.services(core)` — `renderer`
там уже доступен партам как зависимость, сцену можно взять у любого парта
при первом вызове (та же ленивая привязка, что у `MapLayer._attachOccluder`).
`setCamera` остаётся публичным только как путь отхода (или удаляется
вовсе), `Tank` перестаёт быть владельцем центра, `MapLayer.render()` берёт
камеру из сервиса вместо собственного `cameraCenter`.

**Тесты** (`tests/client/levelView.test.js`): `alphaFor` без единого
`setCamera` проецирует по камере сцены; два вызова в одном тике дают один
и тот же центр (`cameraCenter` вызван один раз).

**Документация:** `docs/en|ru/architecture.md`, раздел про сервисы
плагина — владелец центра камеры сменился.
