# Архитектура (игра-плагин)

`vimp-tanks` — **динамический плагин** для [движка VIMP](https://github.com/lgick/vimp-engine)
(публикуется как `vimp-engine` / `vimp-engine-core`): командный танковый
deathmatch, полностью работающий на P2P-инфраструктуре движка (авторитетный
браузерный хост, WebRTC-клиенты, Node.js мастер для лобби/сигналинга). Этот
репозиторий владеет только игровыми правилами — физика, транспорт, эстафета
Worker'ов и MVC/рендер-каркас клиента живут в движке; см. его
[architecture.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/architecture.md)
для полной картины и ADR о разделении движок/игра.

## Структура репозитория

```
index.html / vite.config.js — Vite-root плагина (сборки client/host)
src/
  host/      — HostPlugin: роутер core-событий, TanksBotManager (scripted-
               модуль), команда /bot, системные сообщения b:*
  client/    — ClientPlugin: parts/ (PixiJS-сущности и эффекты),
               bakers/ (процедурные текстуры), хуки, игровой CSS
  config/    — игровые половины конфигов (game.js, client.js, auth.js,
               sounds.js, snapshot.js)
  data/      — статические данные: maps/, models.js, weapons.js
  nodeCore.js — одна ветка на обе половины плагина: браузерный wasm-ассет
               против node-глюe (headless-прогоны)
core/        — vimp-tanks-core (Rust → WASM, pkg-web/pkg-node): танки,
               оружие, боты, предикт, спавн снарядов (см. core.md)
tests/       — поведение host-плагина, JS↔WASM-харнесс, scenarios/
               (headless-прогоны отладки, см. getting-started.md)
scripts/     — обработка аудио, экспорт карт в JSON, манифест, раннер сценариев
```

`src/config/` и `src/data/` читаются Worker'ом хоста движка, клиентским
бандлом и (для карт) мастером движка — всё через контракт плагина
(`HostPlugin.gameConfig`, `ClientPlugin`, `GameManifest`), никогда напрямую
через импорт.

## Как плагин подключается к движку

- **Хост**: `host.worker.js` в движке динамически импортирует `entries.host`
  этого пакета (`src/host/index.js`, дефолтный экспорт `HostPlugin`) и
  вызывает `createCore()`, которая загружает WASM-ядро этого репозитория.
  `TanksBotManager` реализует движковый контракт scripted-модуля
  (`createMap`/`createScripted`/`removeScripted`/…).
- **Клиент**: клиент движка динамически импортирует `entries.client`
  (`src/client/index.js`, дефолтный экспорт `ClientPlugin`) после выбора
  комнаты и вызывает `createClientCore()`.
- **Обе точки входа получают `wasmUrl` в двух видах**: хешированный
  `.wasm`-ассет в браузере и `file:`-URL node-глюe (`entries.wasmNode`) под
  headless-раннером движка. Ветка живёт в `src/nodeCore.js` и намеренно
  общая для обеих половин — headless-прогон на другом ядре, чем у браузера,
  ничего бы не доказывал.
- **Мастер**: код плагина никогда не исполняет — он лишь отдаёт
  `dist/manifest.json` этого пакета и экспортированный JSON карт под
  `/games/tanks/*`.

Полный контракт — [plugin-api.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/plugin-api.md) движка.

## Граница ядра

Только симуляция: физика, танки, оба типа оружия, боты и упаковка бинарных
кадров живут в `core/` (Rust/WASM). Здоровье/боезапас тоже там — JS-панель
лишь проекция событий ядра. Мета (чат, голосования, статистика, раунды,
реестр участников, auth) — движковый JS, полностью параметризуемый конфигом
этого плагина (`HostPlugin.gameConfig`).

## Клиентская сторона

Три механизма сглаживания сети живут в общей машинерии `ClientCore` движка,
а игро-специфичные половины реализованы в Rust-crate этого репозитория:

- **Предсказание** (`core/src/client/predictor.rs`): свой танк симулируется
  репликой авторитетной модели движения (формулы общие с авторитетной
  стороной через `core/src/motion.rs`); хост подтверждает ввод
  (`lastInputSeq`), reconciliation переигрывает неподтверждённые вводы,
  расхождение плавно затухает.
- **Клиентский спавн снарядов** (`core/src/client/shot.rs`): выстрел виден
  и слышен мгновенно, дубли от хоста подавляются по id автора.
- **Интерполяция** полностью движковая (игро-специфичного кода нет).

Рендеринг строится из MVC-компонентов движка + PixiJS-сущностей этого
плагина (`src/client/parts/`) на двух полотнах (`vimp`, `radar`);
процедурные текстуры запекаются при старте из `src/client/bakers/`.

### Жизненный цикл текстур и частиц

- **Владение текстурами**: запечённые ассеты (`bakedAssets` в
  `src/config/client.js`) создаются один раз при старте и общие на всю
  сессию — части, использующие их, вызывают
  `destroy({ texture: false, textureSource: false })`, чтобы собственное
  уничтожение части никогда не освобождало текстуру, которой пользуется
  кто-то ещё. Исключение — `mapSprite` в `Map.js`: его текстура создаётся
  персонально для инстанса карты через `renderer.generateTexture(...)` и
  принадлежит только ему — его `destroy()` передаёт `textureSource: true`,
  освобождая GPU-источник при смене карты.
- **Системы частиц**: `Smoke.js` и `SmokeEffect.js` рендерят частицы через
  `ParticleContainer` + `Particle` (обёрнутые в обычный `Container` внутри
  каждой части, так как `ParticleContainer` принимает только частицы, а не
  дисплей-объекты). Данные симуляции на частицу (скорость, возраст,
  рыскание и т.д.) хранятся в параллельном массиве обычных объектов рядом
  с инстансами `Particle`, поскольку у `Particle` нет `customData`.
  `ParticlePool.js` пулит инстансы `Particle` для переиспользования;
  вызывающий код обязан сам сделать `container.removeParticle(...)` перед
  возвратом частицы в пул. `ImpactEffect.js` остаётся на обычном
  `Container` + `Sprite` — при 2–4 частицах на выстрел накладные расходы
  `ParticleContainer` того не стоят.

## Ключевые инварианты

- **Единый экземпляр PixiJS**: движок и плагин обязаны делить один
  экземпляр модуля PixiJS в рантайме. `pixi.js` — peer-зависимость и
  экстернализирован из client-сборки (`vite.config.js`); host-страница
  резолвит его через import map. Вшитая вторая копия в любой из сторон
  ломает взаимодействие между движковыми renderer/filter-системами и
  PixiJS-объектами этого плагина (baker'ы, `parts/`).
- **Паритет реплики движения**: авторитетное движение (Rapier, в `core/`) и
  реплика клиентского предикта делят формулы тика (`core/src/motion.rs`);
  паритет интеграции закреплён cargo-тестами (`client::predictor::parity`)
  — любая правка движения в ядре или коэффициентов `models.js` требует
  прогона `npm run core:test`.
- Схема snapshot-ключей (`src/config/snapshot.js`) — данные этого плагина:
  незарегистрированный ключ ломает упаковку кадра и на хосте, и на клиенте.
- Совместимость `ENGINE_API_VERSION` проверяется движком при загрузке
  плагина (клиент и хост); при расхождении бандл плагина даже не
  импортируется.
