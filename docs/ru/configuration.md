# Конфигурация (игра-плагин)

Эта страница описывает собственную конфигурацию `vimp-tanks` — игровую
половину контракта, описанного в
[plugin-api.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/plugin-api.md)
движка. Про конфигурацию самого движка (переменные окружения,
`hostDefaults`, конфиг master/lobby, порты/opcodes) — см.
[configuration.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/configuration.md)
движка.

`src/config/game.js` (половина хоста) и `src/config/client.js` (половина
клиента) отдаются движку через `HostPlugin.gameConfig` и
`HostPlugin.buildClientGameConfig()`; `src/config/auth.js` — через
`HostPlugin.authSchema`; `src/config/sounds.js` и `src/config/snapshot.js`
попадают в клиентский конфиг и кодек снапшотов соответственно.

## src/config/game.js — игровой конфиг

Импортирует карты, модели и оружие из `src/data/`.

### Основные параметры

| Параметр | Значение | Описание |
| --- | --- | --- |
| `parts.friendlyFire` | `false` | Урон по своей команде |
| `parts.mapConstructor` | `'Map'` | Имя конструктора карт |
| `parts.hitscanService` | `'HitscanService'` | Сервис расчёта hitscan-выстрелов |
| `mapScale` | `0.3` | Масштаб карт |
| `currentMap` | `'pool mini'` | Карта по умолчанию |
| `mapsInVote` | `4` | Количество карт в голосовании |
| `mapSetId` | `'c1'` | Дефолтный snapshot-ключ конструктора карты |
| `coreParams.levels` | `fallTime: 0.35, fallDamage: 30, fallDamageFreeHeight: 0.5, maxFallDamage: 100, climbGravity: 500, climbMaxSpeedFactor: 0.5, levelAdoptFrames: 8, maxSideEntryRise: 0.5, rampLaunchFactor: 0.35, minLaunchVz: 0.35, maxLaunchVz: 3.5, jumpClearance: 0.45, tiltGain: 2.0, tiltAirGain: 0.12, tiltResponse: 12.0, tiltMax: 0.6, landingShake: { intensity: 3, duration: 220, minImpact: 1.5, fullImpact: 6 }` | Правила 2.5D-уровней, которые движок довозит до Rust-ядра игры как есть (`coreParams` он не читает и не валидирует): `fallTime` — время падения на ОДИН уровень высоты, `fallDamage` — цена одного уровня СВЕРХ мёртвой зоны `fallDamageFreeHeight` (`0` — падение бесплатно): приземление стоит `fallDamage · max(0, высота − fallDamageFreeHeight)`, поэтому дуга ниже мёртвой зоны — прыжок с рампы — бесплатна, а падение ровно с одного уровня стоит `fallDamage · (1 − fallDamageFreeHeight)`. `maxFallDamage` — потолок урона за одно приземление, `climbGravity` — скатывающее ускорение на единицу продольного уклона, `climbMaxSpeedFactor` — насколько уклон 1.0 срезает потолок скорости (`[0, 1)`). Уклон БЕЗРАЗМЕРНЫЙ: движок считает его как `rise * levelHeight / span`, где `levelHeight` — высота уровня карты в мировых единицах (по умолчанию размер тайла), поэтому подъём «уровень на тайл» даёт 1.0, а прогоны демо-карт — от 0.11 (`terraces.rampLong`) до 0.5 (`terraces.rampSteep`). `levelAdoptFrames` — сколько кадров подряд кадр обязан держать уровень ВЫШЕ реплики клиента, чтобы она приняла подъём (уровень ниже принимается сразу: запоздавший кадр врёт только вверх, см. `client::predictor`). `maxSideEntryRise` — потолок скачка высоты при заезде на прогон поперёк оси (в уровнях, граница исключающая). `fallTime` задаёт не длительность напрямую, а ГРАВИТАЦИЮ: падение баллистическое (`vz -= g·dt`), а `g` подобрано так, чтобы падение ровно с одного уровня заняло `fallTime`. Прыжок: `rampLaunchFactor` (безразмерный, `0` — прыжка нет вовсе) — доля вертикальной скорости уклона, уходящая в полёт на сходе с верхнего торца прогона; `minLaunchVz` (уровней/с, `0` — прыгает даже съезд шагом) — порог, ниже которого полёт не начинается; `maxLaunchVz` (уровней/с) — потолок скорости вылета, а с ней и дуги: `maxLaunchVz² / (2·g)`, где `g = 2 / fallTime²`, то есть 0.375 уровня при значениях выше; `jumpClearance` (уровней, `0` — стены пропадают сразу на взлёте) — насколько выше уровня отрыва танк перестаёт видеть стены и перелетает препятствия. Пара — инвариант: пока держится `maxLaunchVz² / (2·g) < jumpClearance`, штатный прыжок до порога не долетает, и перелёт стен остаётся механикой ядра, которую поставляемая настройка не включает никогда, — карта, которой он нужен, поднимает `rampLaunchFactor`/`maxLaunchVz` сама (см. [extending.md](extending.md)). Наклон корпуса: `tiltGain` (безразмерный, `1` — угол равен арктангенсу уклона, `0` — на рампе наклона нет) — во сколько раз уклон превращается в угол; `tiltAirGain` (рад на уровень/с, `0` — в полёте нос не ведёт) — наклон носа по вертикальной скорости; `tiltResponse` (1/с, `0` — корпус замирает на текущем наклоне) — скорость возврата к целевому углу; `tiltMax` (рад, `0` — наклона нет вовсе) — потолок наклона по модулю. `landingShake` — тряска камеры на приземлении, у оружия она задаётся так же (`cameraShake` в `src/data/weapons.js`): `intensity` — сила при полном ударе, `duration` — длительность (мс), `minImpact` — |vz| касания (уровней/с), ниже которого приземление мягкое и тряски нет вовсе, `fullImpact` — |vz|, дающий полную силу (выше — то же самое, `intensity` зажата потолком). Блока может не быть — тогда тряски на приземлении нет, как до её появления. ВНИМАНИЕ: `minImpact`/`fullImpact` численно дублируют блок `landing` из `src/config/render.js` (просадка корпуса, пыль и звук на клиенте) — общего источника у клиентского рендера и WASM нет, поэтому менять их можно только парой, иначе получится камера без пыли или пыль без камеры. Одноуровневая карта их не касается |
| `roomDefaults.maxPlayers` | `8` | Рамка настроек комнаты в лобби: кламп лимита, выбранного создателем (также публикуется в `GameManifest.roomDefaults`) |
| `roomForm` | 5 дескрипторов полей | Схема формы создания комнаты (публикуется как `GameManifest.roomForm`, контракт форм v3 движка): по дескриптору на каждый ключ `roomDefaults` (`maxPlayers`, `roundTime`, `mapTime`, `friendlyFire`, `map`), у каждого — `control` (`text`/`checkbox`/`select`) и `label`; `default` не указывается — движок засеивает значения из `roomDefaults`. Границы времени (`roundTime`/`mapTime`) — в мс; `map` использует `source: 'maps'`, варианты движок берёт из каталога карт. `scripts/build-game-manifest.js` добавляет `regExp` **и** `min`/`max` у `maxPlayers`/`roundTime`/`mapTime` из этих же границ — движок рендерит `min`/`max` подсказкой «(min–max)» рядом с подписью поля и проверяет их на клиенте; авторитетный клампинг остаётся в `applyRoomOverrides.js` движка |
| `scripted` | `namePrefix: 'Bot', defaultModel: 'm1'` | Параметры scripted-участников (ботов): префикс имени `Bot<id>` и модель танка по умолчанию |
| `soundCues` | `roundStart, victory, defeat, frag, death: 'gameOver'` | Маппинг движковых событий на имена звуков этой игры (`SocketManager.sendSoundCue`) |
| `initialVote` | `'teamChange'` | Голосование, отправляемое игроку после первого кадра |
| `spectatorTeam` | `'spectators'` | Название команды наблюдателей |
| `teams` | `team1: 1, team2: 2, spectators: 3` | Команды и их id |

### Статистика (`stat`)

Описывает столбцы scoreboard. Для каждого параметра:

- `key` — порядковый номер ячейки в строке;
- `bodyMethod` — метод обновления в теле таблицы (`=` — замена, `+` — прибавление);
- `bodyValue` — значение по умолчанию;
- `headSync` — синхронизировать body с head;
- `headMethod` — метод обновления в шапке (`#` — количество значений, `=` — замена, `+` — прибавление);
- `headValue` — значение по умолчанию в шапке.

Текущие столбцы: `name` (0), `status` (1), `score` (2), `deaths` (3),
`latency` (4). Движковый механизм Stat пишет только в объявленные схемой
колонки — игра может опустить любую из них.

### Rank/state игрока (`playerState`)

Механику синхронизации (движковая сторона) см. в
[auth.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/auth.md#загрузка-и-синхронизация-rank-и-state-хост)
и
[host.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/host.md#синхронизация-rank-и-state-игрока-этап-b4)
движка. Эта игра объявляет дефолтную форму непрозрачного per-player блока
«скиллов»:

| Параметр | Значение | Описание |
| --- | --- | --- |
| `playerState.defaultState` | `{}` | С чем стартует участник, если у auth-сервиса нет сохранённой записи для него (или он недоступен на входе) |

Движок обращается с `state` как с непрозрачным JSON-блобом — форму
интерпретирует только эта игра. У `rank` (простой числовой аккумулятор
дельты по убийствам, ±1 за фраг) своей конфиг-схемы нет — это просто
число.

### Панель HUD (`panel`)

Схема панели: `fields` — поля со строковыми ключами и дефолтными
значениями ресурсов игрока (обновляются каждый раунд, также уходят в
ядро), `activeKey` — ключ активного оружия в кадрах панели:

- `fields.health` → ключ `h`, значение `100`;
- `fields.w1` → ключ `w1`, `200` патронов;
- `fields.w2` → ключ `w2`, `100` бомб;
- `activeKey: 'wa'`.

Клиентское сопоставление ключей элементам DOM — в `client.js`
(`modules.panel.keys`, включая `t` — время и `wa` — активное оружие).

### Клавиши (`playerKeys`)

Команды игрока. Каждая клавиша имеет битовую маску `key` (`1 << n`,
используется предиктором и ядром в истории ввода) и опциональный `type`:

- `type: 0` (по умолчанию) — многократное действие: начинается на
  keyDown, завершается на keyUp (движение, поворот башни);
- `type: 1` — срабатывает один раз на keyDown (`gunCenter`, `fire`,
  `nextWeapon`, `prevWeapon`).

Соответствие keyCode → команда задаётся в `client.js` →
`modules.controls.keySetList`. Набор наблюдателя — движковый.

## src/config/client.js — игровая половина CONFIG_DATA

Поставляется через `HostPlugin.buildClientGameConfig()`, объединяется
движковым `buildClientConfig.js` со своим `clientDefaults.js`.

### `parts` — игровые сущности

- **`gameSets`** — сопоставление snapshot-ключей классам рендеринга:

  ```js
  gameSets: {
    c1: ['Map', 'MapRadar'],
    c2: ['Map'],
    m1: ['Tank', 'TankRadar', 'Smoke', 'Tracks', 'Dust'],
    w1: ['ShotEffect'],
    w2: ['Bomb'],
    w2e: ['ExplosionEffect'],
  }
  ```

  Один ключ может создавать несколько сущностей (танк рисуется и на
  основном полотне, и на радаре, плюс дым, следы гусениц и пыль).

- **`entitiesOnCanvas`** — на каком полотне (`vimp` или `radar`)
  отрисовывается каждый класс. Сущности можно наследовать и отображать на
  разных полотнах (например, `MapRadar` — упрощённая карта для радара).

- **`bakedAssets`** — процедурные текстуры, «запекаемые» один раз при
  старте (`BakingProvider`, движковый механизм): взрывы, частицы, дым,
  танк, его тень, бомба, следы гусениц, отметки радара. Каждая запись: `name` (id
  текстуры), `component` (кому назначена), `params` (параметры
  генерации). `explosionTexture`, `smokeTexture`,
  `dustTexture` и
  `impactParticleTexture` пекутся одним baker'ом `blurredCircleTexture`
  и различаются только `params` (`radius`, `blur`, `quality`, `color`);
  он возвращает `{ texture, contentSize }`, где `contentSize` — диаметр
  нарисованного круга без запаса под размытие. У `tankShadowTexture` baker
  свой: размытый скруглённый прямоугольник в пропорции корпуса (`width`,
  `height`, `radius`, `blur`, `color`) — самый дешёвый и самый читаемый
  признак высоты (2.5D). Силуэт, а не круг: мягкий ореол круга вылезал
  из-под углов вращающегося корпуса; `contentSize` здесь — ЧЁТКАЯ длина
  фигуры, чтобы масштаб нормировался независимо от запаса под размытие.

  `funnelTexture` печёт не одну текстуру, а набор силуэтов воронки
  (`variants`), из которого `FunnelEffect` берёт случайный, чтобы след
  не повторялся. Заливка двухтоновая: тёмная выемка (`colorFill`) видна
  на светлых картах, светлый бортик выброса (`colorRim`, `rimWidth`) —
  на тёмных. Возвращает `{ textures, contentSize }` с той же семантикой
  `contentSize`. `blur` сильнее ~1/4 `baseRadius` размазывает пятно на
  весь холст, и бортик перестаёт читаться.

- **`componentDependencies`** — какие сервисы инжектируются в компоненты
  (`renderer` → Map, Tank, Tracks, Smoke, Dust, Bomb, ShotEffect,
  ExplosionEffect; `assetsBase` → Map;
  `soundManager` → ExplosionEffect, ShotEffect, Bomb, Tank, Dust; `mapDynamics` →
  ShotEffect; `rampRuns` → Map; `levelView` → Tank, Map, MapRadar, Smoke, Bomb,
  ShotEffect, ExplosionEffect, Tracks, Dust; `localPlayer` → Tank,
  ShotEffect). `mapDynamics` —
  геометрия динамики карты из клиентского ядра (`toWorld(key, localX, localY)`
  поверх `ClientCore.map_dynamics_to_world`), которую в пул кладёт сам плагин
  (`hooks.services`, см. [architecture.md](architecture.md)): эффект выстрела
  держит якорь на теле и спрашивает, где тело нарисовано, в момент рождения
  попадания. Сервис есть только при включённом client-side prediction —
  необъявленный сервис молча приходит как `undefined`. `rampRuns` — сервис
  игры поверх `ClientCore.ramp_runs`: `forLevel(level)` отдаёт прогоны рамп
  уровня в мировых единицах, и по ним слой строит клин горки — ту же
  геометрию, по которой физика ставит стражей, вместо второго обхода грида
  на JS. `levelView` — тоже
сервис самой игры (`src/client/levelView.js`): где, на каком уровне и на
какой высоте локальный игрок. Пишет его локальный `Tank` (что он локальный,
ему сообщает движковый сервис `localPlayer`), читают все, кто обязан уступить
ему видимость, — по одной общей формуле `levelView.alphaFor(level, x, y, z)`:
слои карты и ящики на них, чужие танки, дым, бомбы, эффекты и следы (см.
[architecture.md](architecture.md)). `renderer` парту нужен ещё и затем,
чтобы восстановить по нему центр камеры (`src/client/camera.js`) для
проекции 2.5D.
`assetsBase` — движковая база ассетов этого
  пакета: `Map` превращает её в `${assetsBase}img/<файл>` для тайл-листов
  и спрайтов динамических тел, которые он грузит (см.
  [extending.md](extending.md#новая-картинка-карты)).

### Рендер 2.5D: `seeThrough`, `parallax`, `volume`, `shadow`, `tilt`, `landing`

Все шесть объектов приходят из `src/config/render.js` и лежат здесь как часть
клиентского конфига игры. Источник — именно модуль: партам движок конфиг не
отдаёт (`new Part(data, assets, dependencies, context)` — только сервисы),
поэтому `src/client/levelView.js`, `src/client/parallax.js` и сами парты
импортируют его напрямую. Правка модуля меняет обе стороны сразу.

| `seeThrough` | Значение |
| --- | --- |
| `mode` | `'hole'` — радиальная дыра вокруг игрока (по умолчанию, как в GTA 2); `'layer'` — гаснет весь слой над ним, путь отхода |
| `radius` | Мировые единицы: радиус дыры (режим `'hole'`) |
| `softness` | Доля радиуса, уходящая на затухание края дыры |
| `minAlpha` | Прозрачность в центре дыры |
| `layerAlpha` | Режим `'layer'`: прозрачность всей плиты |
| `fadeRate` | В секунду: скорость сглаживания перехода — мгновенный скачок читается как мигание при каждом въезде под кромку |
| `lowerTint` | Затемнение уровней **ниже** игрока: «темнее — значит ниже» |

| `parallax` | Значение |
| --- | --- |
| `shear` | Насколько объект смещается от центра камеры на ОДИН уровень высоты, долей расстояния до него, И насколько крупнее он рисуется (`1 + z * shear`) — сдвиг и масштаб суть одна проекция. Число ОДНО на всех потребителей — слой уровня и его объём, клин рампы, корпус и обломки танка, следы, дым, бомбы и эффекты: танк на плите уровня 1 обязан смещаться ровно так же, как плита. См. `src/client/parallax.js` |
| `levelZStride` | Шаг `zIndex` между уровнями (`src/client/levelZ.js`). Обязан быть больше любого базового `zIndex` парта, иначе слой моста провалится под наземный навес |

| `volume` | Значение |
| --- | --- |
| `enabled` | `false` полностью выключает экструзию слоёв и клин рампы — путь отхода на слабой машине |
| `slices` | Число срезов экструзии на слой: весь эффект стоит `slices` вызовов отрисовки независимо от числа стен. Только для ОБЪЁМОВ слоёв (здания, перила) — у них боковая грань вертикальная |
| `rampSegments` | Сегментов клина рампы на клетку прогона. Клин — наклонная плоскость (один меш на прогон), это плотность его вершин: сдвиг вдоль прогона растёт квадратично, и от 4 сегментов на клетку ломаная уже неотличима |
| `sideTint` | Затемнение нижних срезов — боковых граней блока и юбки клина рампы |

| `shadow` | Значение |
| --- | --- |
| `scaleGain` | Насколько тень растёт на единицу ПОДЪЁМА над опорой. Тень рисуется ТОЛЬКО в полёте — она признак прыжка или падения, а стоящему на земле танку показывать нечего, — поэтому прыжок на верхнем ярусе выглядит так же, как такой же прыжок на земле |
| `baseAlpha`, `alphaFalloff` | Прозрачность тени на опоре и то, как быстро она бледнеет с ростом подъёма |
| `sizeFactor` | Размер тени долей от ДЛИНЫ корпуса: текстура уже в его пропорции, поэтому в начале прыжка тень лежит ровно под корпусом и из-под него не выглядывает |

| `tilt` | Значение |
| --- | --- |
| `enabled` | `false` возвращает прежний плоский спрайт корпуса: наклон не рисуется вовсе (сами углы хост всё равно считает и везёт) |
| `lift` | Экранный подъём поднявшегося края квада, долей его высоты: пересчёт авторитетных `pitch`/`roll` в углы `PerspectiveMesh` (`src/client/tilt.js`) |
| `vertices` | Плотность сетки `PerspectiveMesh` по каждой оси |
| `shading` | Светотень наклона: во сколько раз меняется яркость корпуса на предельном наклоне. `0` — света нет, картинка как прежде |
| `lightDir` | Направление света в СИСТЕМЕ ЭКРАНА (не корпуса): `[x, y]`, нормируется при чтении. По умолчанию свет с северо-запада — так же освещены боковые грани зданий |

Собственной экструзии у корпуса НЕТ (были `body`, `bodySlices` и
`sideTint`). Боковая грань в этой проекции смещается на
`толщина · shear · расстояние до центра экрана`: у чужого танка на краю
экрана она доходила до длины его же корпуса, разбивалась на ступени и
всегда указывала на локального игрока — центр камеры. Объём танку даёт
только `shading`.

| `landing` | Значение |
| --- | --- |
| `minImpact` | Порог \|`vz`\| касания (уровней/с), ниже которого приземление мягкое: ни просадки, ни пыли, ни звука |
| `fullImpact` | Скорость касания, дающая полную просадку; всё, что выше, к ней и приводится |
| `squash` | Максимальное сжатие корпуса по вертикали, доля (0.14: 0.22 на каждом прыжке читалось как «танк складывается» — просадка обязана быть заметной, но не менять силуэт) |
| `duration` | Длительность просадки и возврата, мс |

Высота уровня в мировых единицах — поле **карты**, а не константа рендера:
`levelHeight` (см. [extending.md](extending.md)). Это величина **физики** —
из неё ядро делает уклон рампы и падение, — и рендер её НЕ читает:
вертикальный масштаб картинки задаёт один `parallax.shear`, и он намеренно
не зависит от карты, иначе слои разных карт разъезжались бы по виду. Карта
с нестандартным `levelHeight` поэтому едет иначе, а выглядит так же.

### `modules.controls.keySetList`

Массив из двух наборов `keyCode: 'команда'`: `[0]` — наблюдатель (`n`/`p`
— переключение наблюдаемого игрока, движковый набор), `[1]` — игрок
(`w/s/a/d` — движение, `k/l/u` — башня, `j` — огонь, `n/p` — смена
оружия). Какой набор активен, диктует хост через порт `17` (KEYSET_DATA).

## src/config/auth.js — конфиг формы авторизации

Приезжает через `HostPlugin.authSchema`: id DOM-элементов (`elems`),
параметры формы (`params`), валидаторы этой игры (`validators`) и тексты
формы (`texts`: `title` + help-секции `{ heading, lines: [{ keys, text,
last? } | { separator }] }`) — движковый шаблон `auth.pug` нейтрален
(заголовок, справочные секции, кнопка `Start`, без поля `name`: ник берётся
из проверенного токена identity лобби, а не из формы), заголовок и
подсказки этой игры подставляет `AuthView` из `texts`. `elems` указывает
`fieldsId: 'auth-fields'` — контейнер, в который движок рендерит контролы
`params` (контракт форм v3; поля `formId` нет — элементом `<form>`
владеет движок). `params` объявляет только собственное поле игры —
`model` (значение по умолчанию, `options`: `control: 'select'` + `label:
'Model'` + список вариантов из `models.js`, `validator: 'isValidModel'`,
ключ `storage` для localStorage) — поля, использующего движковый
`isValidName`, в форме нет. `control` обязателен для каждого поля в
контракте форм v3: поле с объектом `options`, но без `control`, молча
пропадёт (`console.error` + skip в `formBuilder.buildForm`), а не
свалится сборкой. `isValidModel` (модель есть в `models.js`)
инжектируется в движковый `validateAuth` третьим аргументом. Валидация
выполняется и на клиенте (валидаторы из бандла этой игры), и повторно
хостом (Worker) как итоговым авторитетом; по проводу (`AUTH_DATA`, порт 1)
уходят только `elems`/`params`/`texts` — код валидаторов не передаётся.

## src/config/sounds.js — каталог звуков

Каждый звук: `file` (имя файла без расширения, отдаётся из `dist/sounds/`
под `assetsBase` этого плагина), `priority` (выше — важнее при
конкуренции за голоса), `volume`, опционально `loop: true`.
`codecList: ['webm', 'mp3']` — файлы должны существовать в обоих
форматах. Механика воспроизведения — движковый
[client.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/client.md#soundmanager).

`volume` считается против **нормализованных** источников.
`scripts/process-audio.js` указывал `-af` один раз, а это опция *выхода*:
фильтры действовали только на следующий за ней файл — на mp3, то есть
фактически на ветку Safari. Webm, который выбирают все остальные браузеры,
шёл сырым и был разбросан на 11 LU (петля двигателя оказывалась самым тихим
звуком в наборе, взрыв — на 11 LU громче неё). Теперь цепочка фильтров
указана для каждого выхода: все звуки стоят на `I = -16` LUFS, и одно число
`volume` значит одно и то же в любом браузере; `npm run audio:check`
измеряет `build/sounds/` и падает, если два кодека одного звука разошлись
больше чем на 1 LU. Текущие значения пересчитаны по замеренной разнице для
каждого файла, поэтому громкость каждого звука осталась прежней —
относительный баланс не изменился и подбирается на слух.

Петля двигателя (`src/client/parts/Tank.js`,
`calculateEngineSoundParams`) читает `engineLoad` дважды: как высоту тона
(`rate`, от `MIN_ENGINE_RATE` на холостых до `MAX_ENGINE_RATE` на полном
ходу и вплоть до `STRAIN_ENGINE_RATE` при напряжении — газ в стену) и как
громкость (`MIN_ENGINE_VOLUME_FACTOR` → `MAX_ENGINE_VOLUME_FACTOR` от
`volume` выше). На холостых тон ещё и слегка покачивается
(`IDLE_WOBBLE_DEPTH`, `IDLE_WOBBLE_HZ`), сходя на нет с ростом нагрузки:
ровный бас на неизменной высоте ухо слышит как гул, а не как работающий
двигатель. Поэтому `volume` задаётся для едущего танка, а стоящий получает
`0.6` от него.

`tankLanding` — удар корпуса о плиту. Его дёргает не движковый маппинг
событий (`soundCues` в `src/config/game.js`), а сама часть `Dust`
(`registerSound`/`playSound`): приземление видно в кадре по `vz`, а не по
событию хоста, и звучит у каждого танка, а не только у своего. Громкость
берётся от силы касания, мягкое приземление (ниже `landing.minImpact`)
молчит вовсе.

Блок `spatial` переопределяет геометрию пространственного звука — и только
то, что этой игре переопределить необходимо: `mode: 'topDown'`,
`virtualElevation: 108`, `innerRadius: 5`. Движковые дефолты (`180` / `40`)
рассчитаны на масштаб 1:1, а здесь **мировая единица не равна экранному
пикселю**: `mapScale: 0.3` (`src/config/game.js`) вместе с
`baseScale: '5:1'` (`src/config/client.js`) делает мировую единицу впятеро
меньше экранного пикселя, поэтому дефолты растянули бы стереобазу на пять
ширин экрана, а «габаритом игрока» считали бы радиус в пять корпусов. `108`
— половина видимой высоты экрана в мировых единицах (`1080 / 2 / 5`): на
краю экрана (`192` единицы вбок) это угол около 60°, у самого корпуса —
единицы градусов. `5` — полудиагональ корпуса `m1`, а он `8 x 6` мировых
единиц (`size * 4 x size * 3` при `size: 2` в `src/data/models.js`), так что
взрыв внутри габарита распределяется поровну в оба уха. `refDistance` /
`maxDistance` / `rolloffFactor` осознанно оставлены движку.

Оба числа калиброваны под **расчётное окно 1920×1080**; на любом другом
размере движок масштабирует их сам через масштаб сцены, поэтому вариантов
под разрешения не нужно. При этом `108` — по-прежнему расчётная отправная
точка: диапазон подбора на слух 90–150, и точное значение пока никто не
подтвердил — это обоснованный дефолт, а не измеренный. Что означают ключи и
как считается позиция — движковый
[client.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/client.md#soundmanager).

Танк локального игрока регистрируется с `spatial: false`
(`src/client/parts/Tank.js`), и так же — его собственный выстрел
(`ShotEffectController`). Слушатель — центр камеры, то есть сам этот танк:
источник, лежащий ровно на слушателе, HRTF сворачивает не в тишину
панорамы, а в гребенчатую окраску — вместо двигателя гул, — а расхождение
камеры и танка в пару пикселей кидает тот же источник целиком в одно ухо,
потому что азимут в Web Audio зависит от направления, а не от расстояния.
Всё остальное принадлежит миру и панорамируется как прежде.

## src/config/snapshot.js — схема snapshot-ключей

Регистрируется как `HostPlugin.gameConfig.snapshot`: `m1`, `w1`, `w2`,
`w2e`, `c1`, `c2` → числовой id + `kind`, задающий байтовую раскладку
блока (движковый schema-driven packer/unpacker, см. [core.md](core.md)).
Незарегистрированный ключ уронит упаковку кадра.

Строка танка (`m1`) — 16 полей; её хвост: `angvel`, `z`, `level`, `vz`,
`pitch`, `roll`. `z` — визуальная высота (`f32`, `interp: 'lerp'`: подъём по
рампе и полёт обязаны выглядеть плавно), `level` — дискретный 2.5D-уровень
(`u8`, без интерполяции), он переключает zIndex и набор коллизий. `vz`
(`f32`, `interp: 'discrete'`) — вертикальная скорость в уровнях/с, на земле
ноль: по ней клиент узнаёт полёт и силу касания, а реплика своего танка —
фазу дуги (одной высоте отвечают и подъём, и снижение, поэтому восстановить
её из `z` нельзя). Это ЕДИНСТВЕННОЕ поле `m1` без интерполяции, и намеренно:
детектор касания (`src/client/landing.js`) срабатывает на кадре, где `vz`
становится ровно нулём, а сглаженное значение точного нуля чужому танку не
даёт — просадка, пыль и звук приземления у всех, кроме себя, пропали бы. `pitch`/`roll` (`f32`, `lerp`) — наклон корпуса в радианах: его
считает хост, потому что чужие танки наклонить больше нечем. Ширина и
порядок этого хвоста — позиционный контракт сразу с тремя местами:
`TankRow::fields` и `players_json` хостового ядра и `render_overlay`
клиентского.

Уровень едет и в блоках выстрела: строка трассера (`w1`) заканчивается
полями `startLevel`/`endLevel` — уровень начала и конца луча (они
различаются там, где луч упал с кромки), — а бомба (`w2`) и её взрыв
(`w2e`) несут по полю `level`. Клиент мог бы вывести все четыре сам из
своей копии слоёв, но тогда картинка зависела бы от ещё одного
повторённого алгоритма — четыре байта дешевле.

Строка динамики карты (`c1`/`c2`) — `[x, y, angle, z, level, vx, vy,
angvel]`, причём `z` и `level` обязаны объявить `role: 'z'` и
`role: 'level'`: слоёную строку движок узнаёт по РОЛЯМ, а не по именам
полей (имя принадлежит игре), и роль без пары — ошибка загрузки карты, а
не молчаливый возврат к плоской строке. Высота и уровень стоят в ГОЛОВЕ,
а не в хвосте, потому что
покоящееся тело хвост не шлёт вовсе и уровень читался бы нулём — ящик на
мосту «упал» бы у зрителя на землю. `optionalFrom: 5`: динамический элемент
карты шлёт `[vx, vy, angvel]`, только пока движется, — покоящийся ящик
экономит 12 байт в каждом кадре (распаковка всё равно отдаёт полную строку
из восьми полей, отсутствующий хвост — нулями). Полная механика —
движковый
[network.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/network.md#бинарный-snapshot-кадр-порт-5).

## src/data/ — игровые данные

### models.js

Единственная модель — танк `m1`: конструктор `Tank`, стартовое оружие
`w1`, размер (`size: 2`, габариты `size×4 : size×3`), параметры движения
(ускорение/торможение, `maxForwardSpeed: 260`, `maxReverseSpeed: −130`,
поворотный момент, демпфирование, боковое сцепление), физика (`density`,
`friction`, `restitution`), «манера вождения» (пороги и скорости
газа/поворота) и башня (`maxGunAngle: 1.4` рад, скорости
поворота/центрирования).

`brakingFactor: 0.3` — коэффициент торможения: чем выше, тем резче танк
останавливается. Значение намеренно низкое — тело танка создаётся с
предиктивными контактами (см. [core.md](core.md#тело-танка)), и торможению
больше не нужно компенсировать ошибки контакта.

> ⚠️ Коэффициенты `models.js` используются и авторитетным путём ядра, и
> репликой клиентского предикта (`core/src/client/predictor.rs`, формулы
> общие — `core/src/motion.rs`). Их изменение проверяется cargo-паритетом:
> `npm run core:test`.

| --- | --- | --- |

| Тряска камеры | 20px / 200мс | 30px / 400мс |

### maps/

Пять карт: `pool mini` (малая), `canopy`, `garden`, `overpass` (демо 2.5D на
два уровня) и `terraces` (на три). Каждая описывает слои тайлов (`layers`, `tiles`), точки респауна
(`respawns`), статическую (`physicsStatic`) и динамическую
(`physicsDynamic`) физику. Регистрация — `src/data/maps/index.js`. Как
добавить карту — см. [extending.md](extending.md#новая-карта).

#### Поля 2.5D (`levels`, `ramps`)

Формат аддитивен: `map` / `physicsStatic` / `layers` остаются уровнем 0,
поэтому карта без полей ниже грузится ровно как раньше. Эталон на два
уровня — `overpass.js`: земля плюс сквозная эстакада с перилами, двумя
рампами и двумя разрывами перил. Эталон на три — `terraces.js`: терраса
(уровень 1) с верхней площадкой (уровень 2) над ней, рампа 0 → 2 одним
прогоном, ступенчатый путь 0 → 1 → 2, рампа, верхний торец которой упирается
в проезд уровня 0 под плитой, ящики у разрывов перил обоих уровней и
`volumes` у зданий и перил.

| Поле | Значение |
| --- | --- |
| `levels` | Надземные уровни, ключ — номер уровня строкой (`1`). `MAX_LEVELS = 8`, то есть `"1"`..`"7"`; уровни обязаны идти с 1 без пропусков |
| `levels[n].map` | Собственный грид уровня, **той же размерности**, что `map`. `0` — пустота: уровня здесь нет, виден нижний |
| `levels[n].floor` | Тайлы, по которым на этом уровне можно ездить (плита). Тайл перил входит сюда же |
| `levels[n].walls` | Тайлы-стены уровня (перила): блокируют движение и луч на этом уровне и закрывают кромку плиты от выстрела снизу. Каждый тайл `walls` обязан быть и в `floor` — иначе ядро отвергнет карту |
| `levels[n].layers` | Рендер-слои этого грида (`zIndex` → тайлы), базовые значения те же, что у уровня 0; рендер сам сдвигает их на `LEVEL_Z_STRIDE = 100` |
| `ramps[]` | Переходы: `{ tile, dir, from, to }` — индекс тайла в гриде уровня `from`, а `dir` (`north`/`south`/`west`/`east`) — направление, в котором едут, **чтобы подняться** |
| `physicsDynamic[].level` | Уровень, на котором стоит ящик (по умолчанию `0`). Тела разных уровней друг друга не касаются |
| `volumes` / `levels[n].volumes` | Необязательное, **только визуал**: `zIndex рендер-слоя` → его высота в уровнях. Слой с высотой экструдирует сам парт `Map`, и он смещается при движении камеры. Движок валидирует значение и кладёт его парту в `data.volume` |
| `levelHeight` | Необязательное: **мировых единиц на уровень** (до `scale`), по умолчанию — размер тайла. Одно число, которое делает уклон рампы в ядре безразмерным; парту оно приезжает в `data.levelHeight`, движок его валидирует (`vimp-engine >= 0.32.0`) |
| `respawns[team][i][3]` | Необязательный 4-й элемент точки респауна — уровень. Без него уровень выводится из геометрии (`GameMap::level_at`), то есть наземная точка, оказавшаяся под плитой, отправит танк **на** мост |

Рампа — направленный прогон тайлов уровня 0: ядро собирает одинаковые тайлы
в прогоны вдоль оси рампы и интерполирует `z` от `from` к `to` вдоль прогона
(`MapLevels::build`). Уровень щёлкает на середине прогона, а пока центр
корпуса на клетке рампы, танк сталкивается с геометрией **обоих** уровней —
поэтому щелчок никого не выталкивает.

Всё это ядро проверяет при загрузке карты (`MapConfig::validate`) и
отвергает карту с рассинхроном размерностей гридов, дырой в нумерации
уровней, перилами вне `floor`, тайлом рампы, которого нет в гриде, или
номером уровня вне диапазона в `respawns`/`physicsDynamic`. Те же по смыслу
структурные проверки offline делает правило контракта `E4`
(`vimp-contract`).
